# 発注アシスト＆分析基盤 設計（たたき台 v1）

棚卸アプリを「在庫を数える」から「**発注を助ける＋在庫の流れを分析する**」へ拡張するための設計図。
本書は羅針盤（`docs/strategy-10yr.md`）配下の実装計画。実装前に本書で合意を取る。

> **実装状況（2026-07-15 / v0.48）**: フェーズA（汎用2軸・並び替え）✅ ／ B（発注モード・
> 発注履歴・D1 `orders`）✅ ／ D（発注予測: 曜日別学習・推奨発注数）✅ ／ E（履歴カレンダー）✅。
> さらに設計後の追加として入出庫（`useMovements`）・理論在庫（`theoreticalStock`）・
> 発注→入庫のワンタップ取込も実装済み（→ `project-status.md`）。
> **未実装**: F（ミッション表）／ 入数の量子化 ／ 天気の実データ連携。
> C（発注点）は 2026-07-17 に一部実装: 手動発注点 `reorderPoints`・要補充判定・暫定「目安」
> （§2.3 の二段構え）。算出発注点の本実装は需要カレンダー/曜日別モデル完成後。

## 0. 設計思想（最重要）

- **入力はその瞬間に価値を返すものだけが現場で続く。** データ収集のための入力を作らない。現場が元々やっている行為（発注・ざっと在庫確認）に相乗りし、データは副産物で貯める。
- **棚卸＝残高、発注＝フロー。** 2つが揃って初めて消費が見える：
  `消費 = 月初在庫 + 発注(≈納品) − 月末在庫`
  月末棚卸（残高）＋発注記録（フロー）で、**毎日数えずに**品目別の月次消費が出る。
- **軸を切り替える。** 同じ品目が複数の属性を持ち、作業に応じて並べ替え軸を変える：

  | 作業 | 最適な並び |
  |---|---|
  | 棚卸（数える） | 場所別（置き場を歩く） |
  | 発注（頼む） | 仕入先別 |
  | 分析（見る） | ジャンル別 |

- **勘を潰さず、速く・安全にする。** 目安を先に出し、上書きは自由。上書き傾向を学習。
- **甘い数字を出さない（シビアな信頼度）。** データ不足の分析は「参考外」と明示する。

## 2. データモデル変更

### 2.1 分類軸（ジャンル＋汎用2軸）
- `config.axes`: 最大2つのユーザー定義軸 `[{ id:'axis1', name:'場所' }, { id:'axis2', name:'仕入先' }]`
- 品目ごとに軸の値: `item.tags = { axis1:'冷凍庫', axis2:'八百屋青果' }`
- 既存の `category`（ジャンル）はそのまま残す。並べ替え/グルーピングを「ジャンル / 軸1 / 軸2 / 五十音 / 使用」から選べるようにする。
- **メリット**: 場所・仕入先を専用実装せず、名前を変えるだけで両対応。将来の拡張も軽い。
- **グループは事前定義制**: `config.axisGroupsA/B` に定義済みグループ名の一覧を持つ（空グループもOK）。
- **多ロケーション**: `tagsA/tagsB` は各品目の所属グループ名の**配列**（1品目が複数グループに所属可）。軸で並べ替えると、その品目は各グループに**重複表示**される（場所別に各所で数える前提）。
- **振り分けページ**（`AxisAssignModal`・左右2画面）: 左＝ジャンル別アコーディオン（前回0非表示・割り当て済みはグレーアウト）、右＝グループ（作成/リネーム/削除・選択）。右でグループ選択→左で品目タップで追加。既に別グループへ割り当て済みの品目は**確認モーダル**を出してから複数所属に。未割り当ては「その他」。
- **再インポート維持**: 品目名の完全一致で既存の割り当て（配列）を保持、消えた品目は破棄、新規品目は「その他」。CSVに軸列は通常無い前提（あれば `|` 区切りで複数可）。

### 2.2 発注レコード（在庫スナップショットとは別倉庫）
- 在庫（残高）= 既存 `store_history`（`type` 概念を導入し `stock` 既定）
- 発注（フロー）= 新規 `orders`（D1 テーブル＋ローカル）:
  `{ date, supplier(axis), lines:[{ item, qty, unit }], savedAt }`
- 発注量 ≈ 納品量 ≈ 仕入。営業日・信頼度の土台をそのまま再利用。
- **在庫数と発注数は独立入力**（別モード。§3）。

### 2.3 発注点（旧: パー）— 「人間が決める床＋データの推奨」の二段構え
（2026-07-18 提案採用で全面更新 → `proposals.md` 2026-07-17 エントリ）

- **手動発注点＝人間が決める絶対下限（床）**。config フィールド `reorderPoints` として実装済み
  （localStorage/D1/ルーム同期・RoomDO 中継対応）。**予測は手動値を自動上書きしない**
  （推奨はタップ採用のみ。実務は `max(手動床, 推奨)` が安全側）。
- 「要補充」判定は `理論在庫 ≤ 発注点`（未設定品目は 0 以下）。在庫タブのフィルタ・件数・強調が連動。
- 推奨（暫定ヒューリスティック）: `直近30日の平均日消費 × 発注間隔` を「目安」として表示。
  需要カレンダー/曜日別モデルの完成時に置換する。
- **用語の共有語彙**（在庫理論とのレイヤー対応）:
  | 用語 | 意味 |
  |---|---|
  | 発注点（ROP） | **いつ**頼むか＝リードタイム中の予測需要＋安全在庫 |
  | 発注量 | **いくつ**頼むか＝次納品までの予測需要＋安全在庫−現在庫（曜日・外的/内的要因はここ） |
  | 安全在庫 | **切らせない**ための緩衝＝需要のブレ×リードタイム×目標欠品率 |
  | サービスレベル | 許容する欠品率。「絶対切れない」は不可能で、ここを選ぶ問題に帰着する |
- 発注スケジュール（発注曜日/締切）＝リードタイム構造、需要カレンダー（祝日・給料日等）＝外的要因、
  として本設計に接続する。

### 2.4 保留（重いので後回し・モデルは塞がない）
- **多場所（同一品目を場所ごとに数えて合計）**: `item.tags.axis1` は当面単一値＝「並べ替えタグ」。本格版（場所別数量）は必要な店のオプションとして後日。
- **賞味期限**: ロット単位は重い。軽い版＝品目に任意の期限日＋通知から。

## 3. 入力の分離（在庫モード / 発注モード）

- メイン画面に**モード切替**（連続入力トグルの隣など）：
  - **在庫モード**: 数量＝在庫数 → 残高スナップショットへ
  - **発注モード**: 数量＝発注数 → 発注レコードへ（仕入先軸でグルーピング）
- 発注モードでは**予測値をゴースト（薄字）表示**。タップで採用、自由に上書き。
- 「前回と同じ」ワンタップ再利用。

## 4. 発注予測（ラダー：データが要る順）

1. **前回発注量**（発注を記録し始めれば即）← まずここ
2. **曜日平均**（数週間の蓄積後）
3. **天気補正**（外部API＋蓄積、最後。〜2週間は予報／以降は平年値）
- すべて「うすく」出す。信頼度が低い間は目安を控えめに。

## 5. カレンダー履歴

- 年→月→**カレンダー**。各日にマーカー：
  - 🟦 在庫入力あり / 🟧 発注入力あり / 🟩 棚卸（月末指定）
  - 深夜またぎは営業日に寄せて表示
- 日タップ→その日の記録（在庫・発注）
- データ密度が可視化され、ミッション（§6）の動機付けにも直結。

## 6. ミッション／機能解放（ゲームLIKE）

ダッシュボードの「これがあればもっと出せます」を、**進捗バー付きのミッション表**へ進化：

| ミッション | 条件 | 解放される機能 |
|---|---|---|
| 単価をつけよう | 単価入力 | 在庫金額・ABC分析 |
| まず2回 | 棚卸2回完了 | 前回差アラート |
| 発注を記録 | 発注10回 | 発注予測（前回ベース） |
| 曜日をためる | 各曜日3回以上 | 曜日別発注案 |
| パーを決める | パー登録 or 算出可 | 下回り強調・自動発注目安 |

- 解放条件＝**信頼度が“低”を脱する閾値**と一致させる（甘い数字を出さない思想と接続）。
- 早期に簡易版から始め、成長させる。

## 7. フェーズ計画と依存関係

- **済**: 増分1（営業日・月末指定・信頼度・異常検知ユーティリティ）
- **フェーズA**: 汎用2軸＋並べ替え（自己完結・即効・低リスク）
- **フェーズB**: 発注数入力（モード分離）＋発注履歴（フローデータ開始）
- **フェーズC**: パー手動登録＋下回り強調（分析不要で開始 → 算出パーは後）
- **フェーズD**: 発注予測（前回→曜日→天気。Bの蓄積が前提）
- **フェーズE**: カレンダー履歴＋活動マーカー（在庫/発注の複数種が前提）
- **フェーズF**: ミッション表（簡易版は早期、条件が固まり次第拡張）
- **保留**: 多場所（場所別数量）、ロット単位の賞味期限

依存: B→D、(B+棚卸)→算出パー→C強化、(B,在庫)→E、全体→F。

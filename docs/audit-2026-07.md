## 0. 監査で見つかった実バグ（最優先）

### B-01 🔴 config の2つの保存経路でフィールドセットが不一致（軸データ消失）
- `App.vue _configPayload()` は 16 フィールド（axisNames / tagsA / tagsB / axisGroupsA / axisGroupsB / hiddenItems 含む）を送る。
- `RoomDO.js` の `case 'config'`（セッション中のリスト更新）は **10 フィールドしか保存しない**
  → セッション中にホストが品目リストを更新すると、DO 保存・`config_update` ブロードキャストから
  **軸（場所・仕入先）割り当てと非表示品目が脱落**し、ゲスト側の並び替えが壊れる。
- `case 'session_start'` は軸を保存するが **hiddenItems が無い**。
- 原因は「configフィールドの列挙が8箇所にコピペされている」構造（→ R-03）。
- 修正: config のフィールド一覧を共有定数化し、DO 側は 1 つの正規化関数で保存する。

## 1. リファクタリング

### R-01 🔴 `App.vue`（3,450行）の神コンポーネント解体
画面遷移（`currentView` 手動管理・router なし）、セッションライフサイクル、競合解決、
下書き保存、D1 永続化、バーコード、モーダル群、戻るボタン制御が 1 ファイルに同居。
- 分割候補（既存の composable パターンに揃える）:
  - `useSessionLifecycle.js` — onSessionStart / Resume / _reconnectToRoom / draft 保存復元
  - `useConflictResolution.js` — conflictQueue / onResolveConflict / item_add 承認フロー
  - `useBackButton.js` — `_pushBackSentinel` / `_closeTopLayer` 系
  - コールバック登録の初期化ブロック → `wireSyncCallbacks(deps)` として別ファイル化
- `SessionListPage.vue`（1,872行）・`InventoryTable.vue`（1,384行）も同様に肥大傾向。

### R-02 🔴 `useSync.js` のコールバック地獄（25個超の setter）
`setXxxCallback` / `registerXxxGetter` が 25 個以上並び、App.vue と全面密結合。
新メッセージ型を足すたびに「DO → useSync → setter → App.vue」の4箇所改修になっている。
- 案: 単一のイベントエミッタ（`on(type, fn)` / 内部 Map）か、`callbacks` オブジェクト 1 個を
  `initSync({ onUpdate, onRemove, ... })` で一括登録する形へ。B-01 のような取りこぼしが構造的に減る。

### R-03 🟠 config 17フィールドのコピペが8箇所
`useConfig.js` の `_load` / `_saveLocalOnly` / `applyRemoteConfig` / `snapshotConfig` /
`restoreConfigSnapshot` / `setEmptyList` / `loadSampleData` / `clearConfig`、
さらに `App.vue _configPayload` と `RoomDO.js` の2箇所。フィールド追加時に10箇所直す設計で、
実際に B-01 が発生済み。
- 案: `CONFIG_FIELDS`（名前とデフォルト値のテーブル）を `utils/` に置き、
  `serializeConfig(config)` / `applyConfig(config, src)` の2関数に集約。worker 側にも同じ定義を持たせる。

### R-04 🟠 `worker/src/index.js` の `_status` 定型文
`const status = result._status ?? 200; delete result._status` が約10回。
- 案: `respond(result, origin, allowedOrigin)` ヘルパ1つに。あわせて if チェーンのルート定義を
  `[method, pattern, handler, needsAuth]` のテーブルにすると `push/subscribe` が認証ゲート外に
  漏れている類の事故（S-07）も防げる。

### R-05 🟡 `RoomDO._handleMessage`（600行 switch）
メッセージ型ごとにメソッド分割（`_onJoin` / `_onUpdate` ...）し、
`{ type: { handler, hostOnly: true } }` のテーブルで `_isHost` 検証を宣言的に。
audit エントリ生成（id 採番・slice・push・上限切り詰め）が4箇所重複 → `_appendAudit()` に。

### R-06 🟡 その他の重複
- `_genShopCode` の衝突リトライ do-while が `handleStoreCreate` と `handleRegister` に重複。
- `loadFromCSV` と `loadFromCSVMapped` のパース・上限切り捨て・結果構築が重複。
- WS エラーコード → 日本語メッセージのマップが `useSync.js` 内に散在（_connect 内と _handleMessage 内）。

## 3. セキュリティ（優先度順）

### S-A ✅ 対応済み（2026-07-15）ホスト乗っ取り: RoomDO のトークン復旧条件③
> PIN設定店舗はホスト権限の（再）発行に D1 認証トークン検証を必須化（`canGrantHost` /
> `_isStoreProtected` / `_hostAuthOk`、client は join に `authToken` 同梱）。レガシー店舗は
> 後方互換。詳細は `docs/security-review.md` S-A。以下は当時の指摘（記録として保持）。

`RoomDO.js` join 処理: トークン不一致でも「③ 検証済みホスト接続が他に無い」なら
**トークンを再発行してホスト承認**する。
- 攻撃: 店舗コードを知る者（招待URLを受け取った元ゲスト・退職者で十分）が、
  正規ホストのオフライン時に `role: 'host'` で接続するだけで、
  在庫・品目リスト・**単価**・監査ログ・チャット全件を取得し、ルーム解散も可能。
- ②の `sameDeviceHost` も deviceId が自己申告のため詐称可能。
- 対策案: 「トークン喪失からの復旧」は D1 の店舗認証に紐付ける。
  join 時に Bearer トークンを添え、Worker 層で `verifyAuth` に通った場合のみ
  DO へ「ホスト復旧許可」フラグ付きで転送する（DO 単体では判断させない）。
  少なくとも③は削除し、復旧は HTTP dissolve → 再作成に限定する。

### S-B 🔴 PIN 4桁 × SHA-256（既知 S-04 の再強調＋スプレー攻撃）
- ハッシュが `SHA-256(shopCode:pin)`。salt が公開情報（店舗コード）のみで空間は 10^4。
  D1 流出時は全店舗のPINが即時に割れる。
- オンラインでも: 15分5回の制限は**1店舗**への防御。3000店舗時代には
  「よく使われるPIN（1234/0000等）×全店舗」のスプレーで、どこかの店には現実的に入れる。
  IP制限（30回/15分）も分散IPで薄まる。
- 対策: PBKDF2（≥100k iter）＋ランダム salt へ透過移行（計画済み）。
  加えて **PIN 6桁化 or よくあるPINの拒否リスト**、失敗カウントの対象を「shopCode×IP」併用に。

### S-C 🟠 レガシー店舗のフェイルオープン認可（verifyStoreAccess）
PIN 未設定店舗は店舗コードだけで config／inventory／history／orders が読み書き自由。
3000店規模では「PIN未設定のまま運用」が必ず残る。新規は PIN 必須化、
既存は期限を切って移行（未設定店は読み取り専用に降格等）。

### S-D 🟠 /pdf エンドポイントが無認証・サイズ無制限・レート制限なし
`index.js`: 任意の巨大ボディを `arrayBuffer()` で受け、pdfjs を Worker 内で実行。
CPU 課金への経済的 DoS ベクタ。Content-Length 上限（例 5MB）、認証必須化、
`kind='pdf'` の IP レート制限を追加。

### S-E 🟠 CORS / Origin 検証のフェイルオープン（既知 S-08）
`ALLOWED_ORIGIN` 未設定時は Origin 検証をスキップし `Access-Control-Allow-Origin: origin || '*'`。
wrangler.toml の `[vars] ALLOWED_ORIGIN = ""` のままデプロイすると全開放。
本番デプロイ時に未設定なら起動時エラー（またはデフォルト値を本番ドメインに）へ。

### S-F 🟡 認可ゲートの漏れ・不整合
- `push/subscribe` がソフト認証ゲートの正規表現（config|inventory|history|room|orders）の**外**。
  他店の shop_code に自分の端末を購読させ、稼働状況の通知を受け取れる。
- `GET /store/:code`（存在確認・activeRoom 返却）が probe レート制限の**対象外** →
  店舗コード列挙がルームゲートを迂回できる。
- `GET /room/:code/status` は無認証で参加者名・進捗を返す（店舗コード保持者なら誰でも）。

### S-G 🟡 ゲストへ単価（原価）を含む config を送信
`joined` / `config_update` / `session_started` に `prices` を同梱。
アルバイト端末の DevTools で原価が見える。`_sanitizeForGuest`（result API）と同様に
**WS 経路でもゲスト向けは prices を落とす**（ホストのみ受領）。⑤の商業懸念とも交差。

### S-H 🟡 運用衛生
- `auth_tokens` の期限切れ行・`login_attempts`／`ip_attempts` の古い行を掃除する cron が未実装（肥大化）。
- トークンが D1 に平文保存（漏洩時にそのまま使える）。保存時ハッシュ化が安価な強化。
- CSP 未設定（既知 S-07）。`app/public/_headers` に `script-src 'self'` を足すだけの低コスト対策。
- `wrangler.toml` に account_id・database_id がハードコード。公開リポジトリ化・fork 時の事故要因。

## 4. スケール観点（3000店舗以上）

### D1（最重要・一部はバックログ認識済み）
1. **inventory_lines の 10GB 天井**（認識済み）— R2 アーカイブ＋`archive_key` の実装が容量面の最初の壁。
2. **書き込み量**（認識済み）— `saveInventoryToD1` の全量PUT×30秒デバウンスが支配的。
   DO に正があるので「完了時＋数分間隔」に削減。Workers Paid 前提。
3. **`handleRoomResult` / `handleHistoryGet` がスナップショット50件を全件 JSON.parse**
   （最大 ~1MB×50 を毎リクエスト読む）。`store_history` に `session_id` 列を追加して
   1行 SELECT にする。無認証の result エンドポイントで呼ばれるため DoS 耐性にも直結。
4. **`handleOrderCreate` が行ごとに逐次 `await`** — `db.batch()` へ（`insertInventoryLines` は対応済み）。
5. **プラン制限（品目数・台数）がサーバー側で未強制** — `config` PUT の order 長を検証していないため、
   1MB ガードまで品目を積める。DO の在庫も単一キー保存（下記）なので上限強制はスケール防御でもある。

### Durable Objects
- `inventory` / `auditLog` / `messages` が**各1キー**に JSON 保存。DO storage は 128KiB/キー上限。
  品目数千・品目名200字だと `inventory` キーが上限に接触し put が例外化（現在 catch して握り潰し → 静かな同期停止）。
  品目数のサーバー側上限＋超過時のエラー通知を。
- 1店舗=1DO の設計自体は 3000 店に線形スケールする（Cloudflare 的に問題なし）。

### Cron / プッシュ
- `handleCron` が全購読を**直列送信**。3000店×複数端末で実行時間と
  サブリクエスト上限（1000/invocation）に接触する。
  ページング＋`Promise.allSettled` バッチ化、将来的には Cloudflare Queues へ。
- 月末通知は「購読数ぶん」送るため、同一店舗の複数端末に重複配信される（shop_code で1回にまとめる余地）。

### 可観測性
- エラーは `console.error` のみで集約なし。3000店運用では Workers Logpush / Sentry / Analytics Engine で
  「どの店舗で何が失敗しているか」を見られることが前提条件。

## 5. 商業としての懸念点

### C-01 🔴 課金の実効性: プラン判定が完全にクライアント側
- `LIMITS_DISABLED = true` が本番ビルドに焼き込まれ**全員PRO**。課金開始時に
  (a) 戻し忘れ、(b) 戻した瞬間に既存ユーザーの品目が150件に切り捨てられる体験急落、の両リスク。
- 制限を戻しても `localStorage.setItem('tanaoro_is_pro','1')` で誰でも解除可能。
- 対策: `stores.plan` 列を追加しサーバー側で強制（enterprise-design の E0 と同じ）。
  Stripe 実装前でも「サーバーがプランを返す」構造だけ先に入れる。これが**課金開始のブロッカー**。

### C-02 🟠 原価情報の従業員露出（S-G と同じ根）
飲食店では原価をアルバイトに見せない運用が一般的。ゲスト端末に prices が届く現状は
企業導入の商談で確実に指摘される。「価格はホスト/管理者ロールのみ」を仕様化。

### C-03 🟠 退会・データ削除フローが無い
`stores.deleted_at` はあるが API/UI が無い。店名・プッシュ購読・棚卸履歴を保持し続けるのは
プライバシーポリシーとの整合と D1 容量の両面で問題。削除 API＋猶予期間付き物理削除 cron を。

### C-04 🟠 バックアップが D1 Time Travel（30日）頼み
「記録の正」を売りにする以上、誤操作・アカウント事故に備えた定期エクスポート
（cron → R2 に日次ダンプ）を。10年戦略の信頼性の根幹。

### C-05 🟡 単一アカウント・単一ベンダ依存
Cloudflare アカウント1つ（ID がリポジトリに直書き）に本番全資産。
アカウント凍結が事業停止に直結する。最低限、支払い・2FA・トークン権限の分離と、
C-04 のアカウント外バックアップで緩和。

### C-06 🟡 監査ログ200件・チャット平文保存
企業導入では保持期間・削除ポリシー・従業員間チャットの取り扱いを問われる。
`docs/legal/` のポリシーに DO 内データ（チャット・監査ログ・24h TTL）の記載があるか確認を。

### C-07 🟡 サポート耐性
- 認証は「店舗コード＋PIN」のみで、忘れた場合の復旧手段が無い（メール等の連絡先を持っていない）。
  3000店では「入れなくなった」問い合わせが最頻クレームになる。Google OAuth（バックログ済み）か
  リカバリーコード発行を課金開始前に。
- 障害時の告知チャネル（ステータスページ）未整備。

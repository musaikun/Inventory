ステータス: ドラフト（実装前の設計合意用）。**§0（2026-11-28 User決定・D-044）が正**。§1〜§10 は 2026-06 時点の検討で、

## 0. テナント設計（2026-11-28 User決定・D-044）

6月の設計（§9）は「店舗＝共有アカウント・個人のアカウントは作らない」だった。その後、スタッフのログインと役割（migration 0022〜・`staff.shop_code`）、
ログインの見直しの提案（`proposals.md` 2026-10-26：Google／メールのリンク）が入ったため、次の形に改める。

### 0.1 3つの層

```
組織（テナント。請求・データの持ち主）
  ├─ エリア × N（店舗のまとまり。1店は1エリアまで・任意）
  ├─ 店舗 × N（運用の単位。在庫・やること・HACCP の記録・同期のルーム＝今の shop_code）
  └─ 人
       ├─ アカウント（Google／メールのリンク）── 組織の役割（オーナー／本部管理者／エリア担当）または店の役割（店長など）
       └─ スタッフ（名前＋6桁の暗証番号・アカウントなし）── 店ごとに登録（今のまま）
```

- **個人店も「店舗が1つの組織」**（User 決定 1）。登録で組織と店舗が1つずつできる。組織の画面は2店目を足すまで出さない。
  今ある店は、移行のときに1店ずつ組織を自動で作る。
- **スタッフは店で登録する**（User 決定 3）。2店に出る人は、それぞれの店で登録する（記録は店ごとに分かれる）。
- **本部のアカウントは複数持てる**（User 決定 4）。組織の役割:

| 組織の役割 | 見られる店 | できること |
|---|---|---|
| オーナー | 全店 | 請求・契約、店舗の追加・停止・削除、本部の人の招待、配布物の管理 |
| 本部管理者 | 全店 | 配布物（品目マスタ・HACCP・全店共通のやること）の管理、全店の閲覧・集計 |
| エリア担当 | 割り当てたエリアの店だけ | そのエリアの店の閲覧・集計（配布物の管理はしない） |

- **エリアの作り方**（User 決定 4）: 先に全店を登録し、本部が「エリア」を作って、そのエリアに入れる店を選ぶ。エリア担当はエリア単位で割り当てる。
  1店は1つのエリアまで（重なりを作らない）。エリアを作らない組織は、全店をそのまま見る。

### 0.2 組織が配るもの・店が持つもの（User 決定 2）

| 組織が配る（店は書き換えない） | 店が持つ・上書きできる |
|---|---|
| 品目マスタ（名前・単位・分類・入数・**単価**） | 在庫・入出庫・棚卸の履歴 |
| HACCP の衛生管理計画（項目・基準・記録の様式） | 発注点・補充目標・導線（並び）・表示/非表示 |
| 全店共通のやること（定期のやること・チェック表のひな形） | 店で足した品目（**単価もその店で決める**） |
| | やること・チェック表・HACCP の記録（実施の結果） |

- **単価**: 配布した品目の単価は組織が決める（全店同じ）。店で単価を決められるのは、その店で登録した品目だけ。
- 配布物は「配った版」を持ち、店側は版の更新を受け取る。店で足した品目・やることは配布物と混ぜずに持つ。

### 0.3 データの分け方（技術）

- 1つの D1 の中で、行ごとに店（`shop_code`）で分ける今の形を続ける。組織は `stores.org_id` でたどる（全テーブルに `org_id` を複製しない）。
  配布物は組織の行（`org_id`）に置き、店の行から参照する。
- 認可は「アカウント → 所属（組織の役割・エリア／店の役割）→ 店」をサーバーで毎回確かめる。今の `shop_code` の確認の上に1段足す。
- テナントごとに D1 を分ける方式は、大手から物理的な分離を求められたときの選択肢として残す（今はしない）。
- 同期（Durable Object）は今どおり店ごと。

### 0.4 HACCP の記録の保存（User 決定 5：現行の規定に沿う）

- HACCP の記録は**店（組織）の持ち物**。人のアカウントを消しても残す。あとから書き換えない（直すときは訂正の記録を足す）。
- 保存期間の既定は**最後に記入してから1年以上**（東京都の食品衛生管理ファイルの記録表の取り扱い。厚労省の手引書本体には年限の明記が見当たらず、
  自治体で異なりうる）。組織で長くできる（短くはできない）。
- 店舗を閉じても、保存期間が終わるまで記録は残し、帳票（PDF）で出せるようにする。今の削除契約（`account-deletion-contract.md`）は、
  「アカウントの削除」「店の削除」「HACCP の記録の保存」に分けて書き直す必要がある。

### 0.5 店舗間の在庫の移動（User 決定 6：後の段）

- 記録だけでなく、**両方の店の在庫を動かす**: 送る店で出庫、受ける店で入庫。1つの「移動」として結び、受ける店が「受け取った」で確定する。
- 依頼から始められる（受ける店が「これを回して」→ 送る店が送る → 受け取る）。
- FL（食材費・人件費）や PL を出すときに、移動した分の原価を店の間で付け替える土台になる。原価・レシピと同じ時期に作る。

### 0.6 段階（案）

| 段 | 中身 | 本番の変更 |
|---|---|---|
| T-1 | 組織の器（`organizations`、`stores.org_id`）。今の店に組織を自動で作る。画面は変えない | migration・Worker |
| T-2 | アカウント（ログインの見直し L-2）と所属。オーナーをアカウントへつなぐ | migration・Worker・メール送信・独自ドメイン |
| T-3 | 1アカウントで複数の店（店を切り替える）・2店目の追加 | Worker・App |
| T-4 | 配布物（品目マスタ・全店共通のやること）と単価の決まり | migration・Worker・App |
| T-5 | 本部の画面（全店・エリア・エリア担当） | Worker・App |
| T-6 | HACCP の衛生管理計画の配布と記録の保存（HACCP の提案 H-1〜H-4 と合わせる） | migration・Worker・App・法務文面 |
| T-7 | 店舗間の移動（原価・レシピと同じ時期） | migration・Worker・App |

### 0.7 配る仕組みの決まり（2026-11-28 User）

- **自動で反映する。ただし店のデータは消さない・戻さない**（User 決定）:
  - 反映で書き換えるのは「配った項目」（名前・単位・分類・入数・単価・HACCP の項目・共通のやること）だけ。
    店が持つ項目（在庫・発注点・補充目標・導線・表示/非表示・店で足した品目・記録）には触れない。
  - 本部が配布物から外した品目は、店から消さない。「配布終了」の印にして、履歴と在庫は残す（店が隠せる）。
  - 店で直した値（上書きできる項目）は、次の反映で元に戻さない。
  - 同じ名前の品目が店に既にあるときは、重ねて作らずに結ぶ（結ぶ前に店へ確認）。
  - 名前の変更で履歴が切れないよう、品目に**変わらない ID** を持たせる（今は品目を名前で指している。T-4 の前提作業）。
- **店の品目を本部が取り込める**（User 方向）: 現場で品目リストを作った店・データの無い店がある前提で、
  複数の店の品目リストを本部がまとめ（表記ゆれを寄せて）、配布物にできる。取り込んだ品目は、その店では配布物と結ばれる。
- **エリア担当は見るだけ**（User 決定）。

### 0.8 未決

1. **単価の決め方**（User 検討中）: 小さな店は外で買うことが多く、地域で値段が違う。案:
   (a) 配布した単価を既定にして、店（またはエリア）で上書きできる ／
   (b) 品目ごとに「本部が決める／店が決める」を選べる ／
   (c) 今の決定どおり、配った品目は本部の単価だけ。

## 1. 現状と課題

### 現在のデータモデル（フラット構造）

```
stores
  ├ shop_code   TEXT PRIMARY KEY   -- ランダム生成
  ├ store_name  TEXT
  ├ pin_hash    TEXT               -- オーナーの暗証番号（6桁・以前の店は4桁。D-036）
  └ active_room TEXT
```

- 店舗は独立アカウント。上位（企業・本部）の概念がない
- 登録は1店舗ずつ手動（`POST /auth/register` でランダムコード発行）
- **プラン（PRO/無料）はクライアントの localStorage のみ** — サーバーは契約状態を知らない
- 複数店舗を横断する管理画面・集計が存在しない

### 企業導入で顕在化する問題

| 問題 | 影響 |
|---|---|
| 一括発行不可 | 30店舗 = 30回手動登録。コードもバラバラ管理 |
| 本部の管理単位がない | 「この企業の全店」を表現・集計できない |
| サーバー側プラン管理がない | 「30店舗PRO契約」を技術的に表現できない |
| マスター品目の配信不可 | 各店が個別に品目リストを作る二度手間 |

## 2. 目標とする導入フロー

```
① 契約（Web/営業）       本部アカウント作成・PRO契約
② 一括プロビジョニング     店舗名リスト → コード＋初期PIN を一括発行
③ 配布                   本部が各店長へコード＋PINを配布（CSV DL）
④ 各店ログイン            店長がログイン → すぐ棚卸

```

## 3. データモデル（v3 拡張）

後方互換を維持する（既存の個人店舗 = org に属さない店舗 として動作継続）。

### 3.1 新規テーブル: organizations

```sql
CREATE TABLE IF NOT EXISTS organizations (
  org_id      TEXT PRIMARY KEY,             -- 例: ORG-XXXXXX
  name        TEXT NOT NULL,                -- 企業名
  plan        TEXT NOT NULL DEFAULT 'free', -- 'free' | 'pro' | 'enterprise'
  plan_status TEXT NOT NULL DEFAULT 'active',-- 'active' | 'past_due' | 'canceled'
  seat_limit  INTEGER,                      -- 契約店舗数の上限（NULL=無制限）
  billing_ref TEXT,                         -- Stripe customer / 請求書管理ID
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### 3.2 新規テーブル: org_admins（本部管理者）

```sql
CREATE TABLE IF NOT EXISTS org_admins (
  org_id     TEXT NOT NULL REFERENCES organizations(org_id) ON DELETE CASCADE,
  email      TEXT NOT NULL,
  pin_hash   TEXT NOT NULL,
  role       TEXT NOT NULL DEFAULT 'admin', -- 'owner' | 'admin' | 'viewer'
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (org_id, email)
);
```

### 3.3 既存 stores へ列追加（後方互換）

```sql
ALTER TABLE stores ADD COLUMN org_id        TEXT;   -- NULL = 個人店舗（従来通り）
ALTER TABLE stores ADD COLUMN plan          TEXT DEFAULT 'free'; -- org非所属店舗の個別プラン
ALTER TABLE stores ADD COLUMN provisioned   INTEGER DEFAULT 0;   -- 一括発行された店舗フラグ
ALTER TABLE stores ADD COLUMN initial_pin   TEXT;   -- 初回ログイン前の配布用（ログイン後にクリア）
CREATE INDEX IF NOT EXISTS idx_stores_org ON stores(org_id);
```

### プラン判定の一元化（重要）

`isPro()` を **「店舗の実効プラン」** で判定する：

```
effectivePlan(store) =
  store.org_id ? organizations[store.org_id].plan
               : store.plan
isPro = effectivePlan in ('pro', 'enterprise') && plan_status == 'active'
```

クライアントの localStorage は「キャッシュ」に降格し、ログイン時にサーバーの実効プランで上書きする。

## 4. API 設計

### 4.1 一括プロビジョニング

```
POST /org/:orgId/stores/bulk
Authorization: Bearer <org_admin_token>
body: { stores: [{ name: "渋谷店" }, { name: "新宿店" }, ...] }

→ 200
{
  created: [
    { name: "渋谷店", shopCode: "ACME-SHIBUYA", initialPin: "4821" },
    { name: "新宿店", shopCode: "ACME-SHINJUKU", initialPin: "9134" },
    ...
  ],
  skipped: [],          // 重複等
  seatUsage: { used: 30, limit: 50 }
}
```

- seat_limit を超える分は `skipped` に回しエラーにしない（部分成功）
- レスポンスから本部が配布用CSV（店舗名・コード・PIN）を生成できる
- 初期PINは `stores.initial_pin` に保持し、店長の初回ログイン後にクリア＆本人PINへ変更を促す

### 4.2 本部ダッシュボード

```
GET /org/:orgId/overview
→ { stores: [{ shopCode, name, lastInventoryAt, lastItemCount, lastTotalValue, isActiveNow }], totals: {...} }
```

既存の `sessions` / `store_inventory` を org_id で集約するだけで実現可能。

### 4.3 マスター品目配信

```
POST /org/:orgId/master-config/push
body: { config: {...}, targetStores: "all" | [shopCode...] }
```

各店の `store_configs` に本部の標準品目を配信。既存のconfig同期ロジックを流用。
店舗側で「本部マスター + 店舗独自品目」をマージする方針（独自品目は消さない）。

## 9. テナンシー方針の確定（2階層アカウント・フルRBACは採用しない）

検討の結論。詳細な議論経緯はこの節に集約する。

### 9.1 前提の再確認
現状は「**店舗 = 共有アカウント**」。個人ユーザー・ロール・権限は存在せず、
`shop_code + PIN` を知る全員が同一の識別、deviceName は表示ラベルにすぎない。
これは「在庫管理の単位＝店舗」という業種特性に**合った良い割り切り**であり、
弱点ではない。

### 9.2 採用する構造：2階層アカウント
```
本部/組織アカウント   ← 管理・横断閲覧・分析・店舗発行・請求
   └─ 店舗アカウント × N   ← 現状のまま。運用（数える）の単位
```
- **個人ユーザー / memberships / フルRBAC は採用しない**（大工事を回避）。
- 必要なのは「組織」という 1つ上の器と、店舗をぶら下げる `stores.org_id` のみ。
- 数える人（個人）にアカウントは不要。「誰が数えたか」は deviceName で足りる。

### 9.3 なぜ本部（横断閲覧）層は必要か
各店で数えるのは現状のままでよい。だが**横断して見る上位視点**こそ企業が
支払う理由：店舗別ステータス／在庫金額／全店合計／店舗間比較・トレンド。
これは蓄積データの価値が“買い手に見える”唯一の面であり、将来のAI発注・
ロス検知もこのダッシュボードの上に乗る（→ E2）。

### 9.4 将来の芽（今は決め打ちしない）
「SVはエリアA店だけ、部長は全店」のように**管理者の閲覧範囲を分けたい**要望が
出たら、そのとき初めて**本部側だけ**に軽いロール／スコープを足す（例：エリア
単位のサブ管理アカウント）。**店舗運用レイヤーは共有アカウントのまま**。
v1 は「組織アカウント＝全店見える」で出す。

### 9.5 対応表
| 関心 | 対応 |
|---|---|
| 一括契約・店舗発行 | E1 組織＋一括プロビジョニング |
| SV/部長の横断閲覧・分析 | E2 本部ダッシュボード |
| （土台） | E0 サーバー側プラン管理 |
| フルRBAC（users/memberships） | **当面不要** |

## 10. 店舗ライフサイクルと契約変更フロー

課金は組織単位・**有効店舗数（席）**が契約量。「契約変更 = 有効店舗数の増減」。

### 10.1 顧客規模で2トラック
| | 自己申込（中小） | エンタープライズ（大手） |
|---|---|---|
| 課金 | 月額・カード（Stripe）・自動 | 年間契約・請求書・営業経由 |
| 増減 | コンソールで即時・日割り自動 | ベースライン＋超過はtrue-up |
| 反映 | リアルタイム | 更新時/精算時 |
→ **自己申込（Stripe自動増減）を先に**作る。請求書運用は後付け。

### 10.2 店舗の状態機械
```
発行 → 稼働(active) ⇄ 一時停止(suspended) → 削除予約(grace) → 完全削除
        （課金対象）    （課金停止/減額・再開可）  （データ保持・復活可）  （データ消去）
```
これ1本で増減・課金・データ保持を表現する。

### 10.3 増える（店舗追加）
1. 本部が「＋店舗を追加」
2. 契約席数内 → そのまま発行・追加課金なし／超過 → 「追加 ¥X/月（日割り ¥Y）」確認
3. 即発行（コード＋PIN）→ 使用可。Stripe は quantity +1（日割り）
- **発行と課金を連動**（＝有効な店舗＝課金対象。“作ったけど無料”を作らない）

### 10.4 減る（店舗削減）— いきなり削除しない
- **一時停止(suspend)**：季節休業・改装用。データ保持、課金は次期から停止/減額、いつでも再開。
- **削除(remove)**：閉店用。猶予期間（例60〜90日）後にデータ削除。エクスポート案内必須。

### 10.5 課金ポリシー（推奨）
- 追加は**即時に日割り加算**
- 削減は**次の請求サイクルから**（月途中の返金なし＝SaaS標準・予測可能・不正防止）
- 季節営業は**停止**で回す

### 10.6 決めておくこと
1. 課金対象の定義：active な店舗＝1席（suspended は課金外）
2. 年間契約の超過：**ソフトキャップ**（運用は止めず超過を後精算）。ハードキャップは現場が困る
3. データ保持期間：削除予約後 60〜90日＋エクスポート必須
4. 操作できる人：本部の owner/admin だけ（店舗は自分を消せない）
5. 監査ログ：誰がいつどの店舗を増減したか（エンタープライズ必須）

### 10.7 実装の位置づけ
- 発行・停止・削除・状態機械・データ保持・監査 → **E1**
- 課金の自動増減（Stripe quantity・日割り・請求書） → **E4**
- 順序：E1で状態機械を正しく作れば、E4は「active店舗数を数えて Stripe quantity に反映」するだけになる。

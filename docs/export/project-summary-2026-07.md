## 1. プロダクト概要

**タナオロ** — 飲食店の棚卸作業を高速化するスマホ Web アプリ（PWA）。

- **課題**: 棚卸は月1〜2回・閉店後に紙とペンで2〜3時間。集計ミス・転記漏れ・属人化。
- **解決**: 音声入力 → 辞書変換 → 在庫記録。複数端末リアルタイム同期で分担作業を即時合算。
- **対象**: 飲食店オーナー・店長・パート従業員（技術知識不要）。
- **提供形態**: PWA（ブラウザ）＋ TWA（Google Play アプリ版・リーダーアプリモデル）。

## 2. アーキテクチャ

```
ブラウザ(PWA: Vue 3 + Vite)
  │  HTTPS REST / WebSocket
Cloudflare Workers (ルーター・認証・レート制限)
  ├── D1 (SQLite) …… 認証・店舗・セッション・在庫・履歴・発注の「正」
  └── Durable Objects (RoomDO) …… 1店舗=1DO。WebSocketハブ・在庫同期・auditLog
ホスティング: Cloudflare Pages ／ 全資産 Cloudflare に統一
```

- **設計の要**: `shopCode`（店舗コード）= DO ルームID = テナントキー。D1 は全クエリ `WHERE shop_code = ?` で分離。
- **認証**: 店舗コード + PIN（PBKDF2 100k反復・ランダムsalt）→ Bearer トークン（30日・D1管理）。
- **同期**: ホスト/ゲストモデル。ゲストは参加時必ずホストの状態に揃う。オフラインは `updatedAt` タイムスタンプでマージ。3秒以内の同時入力は競合バナー（合計/自分/相手の3択）。
- **型なし（TypeScript不使用）**・Vue 3 `<script setup>` 統一。

## 3. 実装済み機能（v0.48）

### 入力・取込
- 音声入力（Web Speech API）＋品目別辞書による誤認識補正
- テキスト・バーコード・CSV / Excel / PDF 取込（PDF列マッピングのレシピ保存）
- 同名品目の統合・ゲスト品目追加→ホスト承認フロー

### 棚卸・同期
- 複数端末リアルタイム同期（DO + WebSocket）・競合解決・オフライン再接続マージ
- 招待リンク共有（ルーム限定URL: その回のセッションIDが鍵・完了後は3日間結果閲覧）
- チャット・変更履歴（auditLog: 誰が/いつ/何を/何個）・参加者別実働時間

### 発注・入出庫（在庫の環）
- 発注セッション（オレンジテーマ）・適正在庫の曜日別学習・推奨発注数
- 入出庫記録（グリーンテーマ・`MovementPage`）・発注→入庫のワンタップ取込
- 理論在庫（直近棚卸残高＋その後の入出庫の純関数）とズレ検出

### 分析・管理
- 在庫分析ダッシュボード（在庫金額・前回差・ABC・曜日・信頼度）
- 履歴カレンダー（棚卸/発注/入出庫の統合表示・種別フィルタ・金額概算）
- 分類軸（場所・仕入先など最大2軸・1品目複数グループ・ドラッグ並び替え）

### 基盤
- D1 永続化・監査ログ・プッシュ通知・端末間アカウント設定同期
- 無料/PROプラン制限の骨組み＋サーバー側プラン管理の土台（14日トライアル導出）
- TWA 対応（アプリ版は価格非表示＝Play課金ポリシー回避）

## 4. 長期戦略（4フェーズ）

> 選別基準: **「もし AI がすでにデータを持っていたら、我々はまだ必要か？」**
> 物理現実の捕捉点を押さえ、記録の正になり、AI の競合ではなく手足になる。

| フェーズ | 内容 | 状態 |
|---|---|---|
| 1 | 棚卸を速くする道具 | ほぼ完成（現在） |
| 2 | 本部×多店舗の在庫基盤 | 設計済み |
| 3 | AI発注・ロス検知・最適化 | 未着手（データが燃料） |
| 4 | 仕入先連携・取引決済 | 未着手（最大の市場） |

**実行順の原則**: 蛇口（現場高速化）→ 燃料（データ捕捉）→ 価値（分析）→ 配送車（企業インフラ）。
買うのは現場ではなく上層部。PMF 前にスケールへ過剰投資しない。目標: 導入3000店舗。

## 5. 料金戦略（確定・実装は保留）

**リバーストライアル型**: 登録から14日フル機能 → 未課金なら「無料の床」（入出庫＋品目マスタ）へ降格。

- 有料は **2,980円/月 の1本のみ**（複数tierなし・サブスク一択）。ZAICO（11,400円〜）の 1/4 価格帯。
- 降格の体験設計が成否の9割: **作ったデータは消さない**・品目マスタは床へ引き継ぐ・「贈り物」フレーミング・レビュー依頼は感動の瞬間（7〜10日目）に。
- サーバー土台は導入済み（`stores.plan` 列＋トライアル導出）。クライアント配線と Stripe が残。
- Google Play 版はリーダーアプリモデル（価格・決済導線を出さない）。

## 6. セキュリティ現況（2026-07-15）

### 対応済み
| ID | 内容 |
|---|---|
| S-01/S-05 | ログイン総当たり対策（店舗単位 5回/15分 ＋ IP単位 30回/15分） |
| S-02 | データ系APIのソフト認証（PIN設定店舗は Bearer 必須） |
| S-03 | ペイロード上限 約1MB |
| S-04 | PIN ハッシュ PBKDF2（100k反復・ランダムsalt・透過移行） |
| S-06 | ルームコード総当たり対策（D1存在チェックで DO 起動前に404） |
| S-A | ホスト乗っ取り対策（ホスト権限の再発行に D1 認証トークン必須） |
| S-10 | クロスアカウント漏洩対策（アカウント切替時のローカル全消去） |

### 未対応（優先度順）
1. CORS フェイルオープン（`ALLOWED_ORIGIN` 未設定で全開放）— 小改修
2. `/pdf` 無認証・サイズ無制限 — 経済的DoSベクタ・小改修
3. CSP 未設定（トークン localStorage 平文）— `_headers` 1ファイル
4. WS ゲストに単価（原価）が届く — 企業商談の失注要因
5. レガシー店舗（PIN未設定）のフェイルオープン認可
6. PIN 4桁のスプレー攻撃耐性（6桁化 or 頻出PIN拒否）
7. 認証テーブル掃除 cron・トークン保存時ハッシュ化

## 7. 現在の最優先課題（Wave 2.5 — 信頼性と収益化準備）

課金開始・Play公開・企業商談の**どれに進んでも前提**になる項目:

1. **セキュリティ小改修**（上記 1〜4。合計半日規模）
2. **入出庫の D1 同期** — 現状 localStorage 専用。「無料の床＝入出庫」戦略の前提条件
3. **日次バックアップ**（cron→R2・リストア検証込み）— 現状 D1 Time Travel 30日のみ
4. **退会・アカウント削除フロー** — Google Play の必須要件（アプリ内＋Web削除手段の義務化）
5. 最小監視（Sentry/Logpush）＋認証テーブル掃除

### 法務の宿題（課金開始と同時）
- 特定商取引法に基づく表記・総額表示
- プライバシーポリシー改定（Stripe 導入でメール収集が実質必須になる／現行は「メール非収集」建て付け）
- Play Data Safety フォーム（操作ログ・IPログの申告整合）

## 8. 主要な意思決定の記録

| テーマ | 決定 | 理由 |
|---|---|---|
| 無料プラン | 150品目 / 履歴直近1回 / 同期3台 | 体験(同期)は触らせ、履歴・規模で課金転換 |
| 課金 | Web=Stripe 主体・2,980円1本 | 手数料・全デバイス対応・複雑さ回避 |
| Play対応 | リーダーアプリモデル | Google Play 課金ポリシー回避 |
| ホスト同時ログイン | 1端末制限（単一トークン） | 多重ホストによるセッション破壊防止 |
| 企業導入 | 設計のみ先行 | 引き合い前の過剰投資回避 |
| AI | 方針確定・実装保留（フェーズ3） | データが貯まってから |
| 表記ゆれ自動マージ | 不採用 | 誤検出多（サーモン/鮭/スモークサーモン問題）。手動マージ＝エイリアス学習の入口として将来小さく |
| 公開API | 課金する連携先が出るまで作らない | 早すぎる公開は負債 |

## 9. 既知のリスク（トップ5）

1. **原価の従業員露出**（ゲスト端末に単価が届く）→ 企業導入の失注要因
2. **入出庫データ消失**（localStorage専用）→ 無料床ユーザーの機種変更で全損＝★1レビュー
3. **バックアップ不在** → Cloudflare アカウント事故で全店舗履歴喪失・回復不能
4. **削除フロー不在** → Play 審査リジェクト
5. **App.vue 3,400行の神コンポーネント** → 同期バグ混入率の慢性リスク（分割は専用セッションで）

## 10. 開発運用

- **セッション分業**: 実装/バグ修正セッション ↔ PM セッション（PM・アーキテクト・QA・セキュリティ・docs管理）
- **新機能の共通チェックリスト（DoD）**: UI3サイズ・バリデーション・エラー処理・権限・多店舗・多人数・同時操作・オフライン・戻る操作・通知・テスト・docs 等（`docs/feature-checklist.md`）。実装側がセルフチェック → PM が取り込みレビューで再照合
- **デプロイ**: GitHub Actions。main merge=本番 / claude/** push=プレビュー。手動フォールバック `./scripts/deploy.sh`
- **docs 駆動**: 決定は会話でなくファイルに残す。各文書は「最終更新/位置づけ」ヘッダを持ち、完了した設計書は削除せず「実装済み（記録）」へ格下げ

## 11. 用語集

| 用語 | 意味 |
|---|---|
| shopCode | 店舗コード。テナントキー＝DOルームID＝D1分離キー |
| ホスト / ゲスト | ルームの主催端末（全権）と参加端末（入力のみ・原価非表示） |
| hostToken | DO が発行するホスト認証トークン（再接続時に検証） |
| セッション | 棚卸/発注の1回分。sessionId で新旧を区別 |
| 軸（axis） | 品目の分類軸（場所・仕入先など最大2軸・ユーザー定義） |
| 理論在庫 | 直近棚卸残高＋その後の入出庫から導出した推定現在庫 |
| 営業日 | 深夜またぎを前日扱いにする業務日付（切替既定5時） |
| リバーストライアル | フル14日 → 無料の床（入出庫のみ）へ降格する料金モデル |
| 無料の床 | 降格後も使える範囲（入出庫＋品目マスタ）。ZAICO難民の受け皿 |
| DO（Durable Object） | Cloudflare のステートフル実行単位。1店舗=1DO |
| TWA | Trusted Web Activity。PWA を Play ストアアプリとして配布する仕組み |
| auditLog | 誰が・いつ・何を・何個の操作記録（DO内・最大200件、完了時に履歴へ永続化） |

# 24 運用・障害対応 ★追加分類

スナップショット: 2026-07-15 / v0.48
状態: **運用の空白地帯**（監視・バックアップ・runbook すべて未整備 = Wave 2.5 の中心）

## 現状わかっている挙動（障害時）
| 障害 | 現在の挙動 |
|---|---|
| D1障害 | レート制限は素通し（フェイルオープン）・ログインは止まる可能性・ホスト復旧はレガシー扱い |
| WS切断 | クライアントが自動再接続 → updatedAtマージ。DO storage put 失敗は握り潰し（静かな同期停止リスク） |
| デプロイ失敗 | CIのテストゲートで本番反映前に停止。migration漏れ事故は deploy.sh/CI で再発防止済み |

## 整備すべきもの（優先順）
1. **日次バックアップ**: cron → D1全テーブルをR2へエクスポート。**リストア手順の実地検証まで**が1項目。Cloudflareアカウント外への二次コピーも検討（アカウント凍結=事業停止の緩和）
2. **監視**: Workers Logpush or Sentry。最低限「店舗単位のエラー率」「D1書き込み失敗」「WS接続失敗率」
3. **runbook**: 「D1が落ちた」「Workerがエラーを吐く」「特定店舗だけ同期しない」の初動手順
4. **ステータスページ**: 簡易でよい（障害告知チャネル。現状ユーザーへの告知手段がない）
5. 認証テーブル掃除cron（auth_tokens期限切れ・login_attempts/ip_attempts古い行）

## 単一障害点（意識しておく）
- Cloudflareアカウント1つに全資産（Pages/Worker/D1/DO）。支払い・2FA・トークン権限の分離を
- 運営者1名（バス係数1）。復旧手順の文書化は自分のためでもある

## 定期メンテナンス（忘れると壊れる系）
- **祝日ロジックの年次確認**: `jpHolidays.js` は祝日法ベースの計算式（有効域1980..2099）。
  **祝日法の改正・特例移動（五輪型）があったら手動更新が必要**。毎年12月に翌年分を目視確認。
- 給料日既定（25日）・長期休暇スパンは全国一律ヒューリスティック。店舗からの指摘が
  溜まったら店舗別設定化（→ 21 アイデア）。

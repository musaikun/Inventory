## 実装

- migration 0028 `login_guard`（店×アカウント。IP・端末IDは持たない）＋ `worker/src/loginGuard.js`。
  確かめる**前**に1回ぶんを1つの UPSERT（`RETURNING`）で数え、ロック中は何も通さない。5回ごとに 15分→30分→1時間→…→24時間（上限）と倍。
  7日あいたら数え直し、正しい暗証番号で消える。店にいない名前も同じに数える（ロックの出方で名前の有無が分からない）。
- IP 単位（`rateLimiter.reserveIpAttempt`）: 確かめる前に1つの文で数え（`INSERT … SELECT … WHERE COUNT < 上限`）、失敗でなければ数から外す。
- スタッフの管理者解除（`unlock`）は `login_guard` を消す。account削除は `login_guard` も消す。毎時 cron で期限切れを消す。
- 障害時: rate-limit table と同じくフェイルオープン（D-015）。`login_guard_unavailable` を security event に残す。
- プライバシーポリシー（docs・app・landing の3つ）: 記録の名前・目的・保存期間（最後の失敗から7日）を変更、端末IDを外した。

## オーナー PIN の6桁化（2026-10-13・User「オーナーPINも6桁にして進めて」）

- `worker/src/pinPolicy.js`: 6桁・同じ数字だけ／連番／くり返しは不可（スタッフと共通。staffHandler から移した）。
- 登録は6桁だけ（400 `weak_pin`）。`stores.pin_digits`（migration 0029）に 6 を入れる。NULL は以前の4桁。
- ログインは4桁のままでも入れるが、`pinUpgradeRequired: true` を返す（`/auth/me` も同じ）。
  App は `PinUpgradeModal`（閉じるボタンなし）を出し、`POST /auth/pin` で6桁へ変えるまで続けさせない。
- `POST /auth/pin`: オーナーの token だけ。新しい PIN の決まり・同じ PIN を先に断り、今の PIN の確認は段階的なロックに載せる。
  変えたら `pin_digits = 6`、この端末以外のオーナーの token を消す（4桁が知られていた場合に相手を切る）。スタッフの token は残す。
- account削除の再認証は6桁、まだ変えていない店は4桁を受け付ける。
- 画面: 登録・ログイン・削除（モーダルと公開ページ）の PIN 欄を6桁に。ログインと削除は以前の4桁も入れられる。

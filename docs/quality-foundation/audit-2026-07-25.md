## 重大な発見

### 1. WebSocket の join が認可境界になっていない

`RoomDO._handleMessage()` はメッセージ種別へ直接分岐し、参加成功を全更新の前提として
強制していません。`join` より前に `update`、`remove`、注文、棚卸、chat、
品目追加要求、競合 lock などへ到達できる構造です。

さらに、空の `deviceId` は参加者上限を数える一意 ID 集合に入りにくく、接続数制限を
回避する余地があります。`conflict_lock` はコメント上ホスト限定でも、同等の server 側
判定が見当たりません。

対応タスク: `SEC-001`

### 2. 注文 upsert に店舗所有確認がない

`handleOrderCreate()` は注文 ID を global な conflict key として更新します。
movement 側には既存 ID の owner check がある一方、order 側にはありません。
別店舗が同じ ID を送ると、既存注文 header の `shop_code` を変えずに内容だけ更新する
越境書き込みが成立する可能性があります。

対応タスク: `SEC-002`

### 3. cron が現行 schema にない列を使う

`pushHandler.js` の stale session query は `sessions.updated_at` を参照します。
現在の sessions table の migrations にはこの列がありません。日次処理はこの地点で
例外になり、後続の cleanup を完了できない可能性があります。

対応タスク: `BUG-001`

### 4. Push 購読の認証と入力検証が不足

`/store/:code/push/subscribe` の POST / DELETE は現在の認証適用範囲から外れています。
購読 endpoint と key の構造・長さ・URL も十分に制約されていません。

対応タスク: `SEC-003`

### 5. D1 障害時の認可判定が fail-open

ルーム入口の店舗存在確認と Durable Object 内の保護店舗判定は、D1 例外時に処理継続または
legacy 店舗扱いへ倒れます。可用性のための fail-open は読み取りや統計では選択肢になりますが、
ホスト権限の新規取得境界には不適切です。

対応タスク: `SEC-004`

### 6. Durable Object 休止で保留要求が失われる

品目追加要求の応答先 WebSocket は `_itemAddRequests` という in-memory Map だけにあります。
WebSocket Hibernation 復帰では constructor が再実行され、通常のメモリ状態は引き継がれません。
未応答要求の件数上限もないため、長時間稼働時のメモリ増加も考慮が必要です。

対応タスク: `DO-001`

  差し込む構造であり、今回の確認範囲では直ちに XSS と判定しませんでした。

  直ちに不具合とは扱わず収益化前の blocker として残します。

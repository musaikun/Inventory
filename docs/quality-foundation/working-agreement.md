# 共同作業ルール

最終更新: 2026-11-02

読む順番、検証コマンド、version、push の権限は [`AGENTS.md`](../../AGENTS.md) を正とします（D-029）。
ここには複数のセッション・agentが並行して作業するときの決まりだけを置きます。

## セッション開始

1. `git status --short --branch` で現在 branch と既存差分を確認する。
2. `AGENTS.md` の「読む順番」の段階1を読む。
3. 対象タスクを一つ選び、`task-list.md`（状態の正本）の状態と担当を更新する。
   詳細と作業記録は `tasks/<ID>.md` に置く。優先度・状態・担当は`task-list.md`だけで管理する。
4. User の判断で結果が変わる不明点は、実装前に User へ確認する。決まったら `decisions.md` へ記録する。

## 実装

- ユーザーの差分と、別のセッションが担当中の差分を上書きしない。
- セキュリティ修正は、成立条件を示す失敗テストを先に追加または同じ差分に含める。
- バグ修正と大型 refactoring を同じタスクに混ぜない。
- DB migration は後方互換性、rollback 不能性、既存データを確認する。
- Cloudflare API、制限、設定は、実装時点の公式文書で再確認する。
- deploy、本番 migration、外部サービスの変更は User の明示依頼がある場合だけ行う。
  commit・push の権限は `AGENTS.md`・`CLAUDE.md`（D-022）に従う。

## 検証

コマンドは `AGENTS.md` の「コミット前の検証」。App と Worker は個別に実行して結果を報告する。

- 依存を変えたら `npm audit --omit=dev` と `npm outdated` も見る。
- `TEST-002`のcritical integration/E2Eが残る間は、unit test成功だけで同タスクを完了にしない。
- 既知失敗が残る場合は「全件成功」と表現しない。

## 完了・引き継ぎ

1. タスクの完了条件を確認し、検証結果を `tasks/<ID>.md` に記録する。
2. API、DB、認可、ユーザー操作、運用が変わった場合は関連文書を同じタスクで更新する（D-028）。
3. `task-list.md` の状態を `レビュー待ち` または `完了` にする。完了した `tasks/<ID>.md` はそのまま残し、
   `task-list.md` の「完了」表へ行を移す（詳細fileの移動・集約はしない）。
4. `sessions/` に新しいファイルを作り、変更、検証、残件、次の一手を書く（D-033）。
5. 未追跡ファイルと意図しない差分がないか `git status` で確認する。

現在のWeb release判定は`web-release-readiness.md`を使用し、production URLのUser確認を必須とします。
Google Play releaseでは`quality-scorecard.md`をCodexとClaude Codeが独立して評価します。

## 競合時

- 同じタスクが `進行中` なら、その担当者の完了または明示的な引き継ぎを待つ。
  ただし担当の記録が **14日以上更新されていない** 場合は、User の承認を得て引き継いでよい。
- 別タスクでも同じファイルを触る場合は、先に小さい方を完了させるか担当を調整する。
- 文書と実装が矛盾したら、**現在の実装を正として文書を合わせる**（D-028）。
  ただし実装がバグに見える場合や、どちらに合わせるかで製品の挙動が変わる場合は User へ確認する。

## 判断・提案

- 採否は User が承認する（D-030）。PMセッションは置かない。
- User が依頼・承認した仕様は採用済みとして扱い、恒久docsへ反映する。
- User が明示していない設計判断は `docs/proposals.md` に投稿し、User の承認を待つ。

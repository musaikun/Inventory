- 新規提案は**日付見出しで先頭に追記**する（新しいものが上）。
- 1提案 = 概要 / 背景・根拠 / 影響範囲・実装状況 / PM判断。
- **PM判断**の状態: ⬜未トリアージ ｜ ✅採用（→反映先ファイル） ｜ 🕓保留 ｜ ❌却下。
- PMが恒久docs（strategy / roadmap / project-status / pricing-strategy / ordering-analytics-design 等）へ
  反映したら、ここのエントリは削除せず「✅採用（→ファイル名）」に落として記録として残す。
- 実装済みの提案でも、**設計判断としてdocsに残すべきか**の判断はPMが行う（実装＝合意ではない）。
- 現行fileは2026-09以降を保持し、それ以前は下記の月別archiveへ移す。archiveは追記・現行化しない。

## 2026-10-08: App の PDF.js（pdfjs-dist）は 5.6 のまま据え置く（提案元: User依頼のセキュリティ確認 / Claude Code）

- **概要**: `pdfjs-dist` 5.6.205 は既知の脆弱性 GHSA-hq66-cqwq-w95j（細工したPDFでスクリプト実行、修正は 6.2.108）の範囲にあるが、今は 6 系へ上げない。
  代わりに、脆弱性の前提に当たらないことをテストで固定し、PDF を開く設定を明示した（`app/src/utils/pdfjsOptions.js`）。
- **背景・根拠**: 公開情報では前提が「`enableScripting` 有効（pdf.js ビューアの既定）」と「スクリプトを許す CSP」。回避策は「`enableScripting` を false にするか CSP を設定する」。
  App は canvas への描画と文字の取り出しだけで、注釈レイヤー・PDF内スクリプト・ビューア部品を使わない。公開 CSP は `script-src 'self' 'wasm-unsafe-eval'`（inline・eval 不可）。
  一方 6.0 で対応ブラウザが **Safari 18 / Chrome 125 以上**に上がり（pdf.js #21152）、iOS 17 以前の端末で PDF 取込が動かなくなりうる。
- **影響範囲 / 実装状況**: 実装済み（v0.152.8）。`getDocument` は `pdfDocumentOptions`（`isEvalSupported:false`・`enableXfa:false`）だけを通す。
  `pdfjsOptions.test.js` が「getDocument は共通設定だけ」「AnnotationLayer / enableScripting / pdf_viewer を使わない」「CSP が inline・eval を許さない」を固定。
  Worker 側の pdfjs は `/pdf` 廃止で削除済み。ほかの依存の指摘（vue 3.5.43 / nanoid / source-map-js / dompurify）は互換範囲で更新した。
- **PM判断（User）**: ⬜ 6 系へ上げる時期（PDF取込の対象を iOS 18 以上に絞ってよいか）

## 2026-10-08: スタッフ権限を古いAPIでもサーバーで守る（金額・削除）（提案元: User依頼のセキュリティ確認 / Claude Code）

- **概要**: 段 2-3 の役割の権限を、権限チェックの無かった古い API（config / history / orders / movements）にも効かせる。
  金額（`money`）の無い人には単価・小計・在庫金額を落として返し、その人からの保存では金額をサーバーの前の値から戻す。
  あわせて未使用の `/store/create`（PIN の無い店舗を認証なしで作る）を廃止した。
- **背景・根拠**: 金額は画面で隠していただけで、アルバイトのトークンで `GET /store/:code/config` や `/history` を直接呼べば単価・在庫金額が読めた。
  履歴・発注・入出庫の削除も役割を見ていなかった。新しいセッション系 API は既に `_requirePerm` で守っている。
- **判断したこと（PM確認したい点）**:
  - 金額の無い人が config で単価を送ってきたら、**403 ではなく無視**（前の単価を残して 200）。その人の端末は単価を持っていないので、丸ごと PUT は常に「単価が空」になる。403 にすると品目を足す（誰でもできる）が通らなくなる。既存テスト（staff.test.js の単価変更 403）はこの挙動へ書き換えた。
  - 履歴の訂正・ロック（丸ごと POST）は、金額を前の版から戻す。数量を訂正した品目の小計と在庫金額はサーバーの単価で計算し直す（端末の訂正と同じ式）。
  - 棚卸の完了（`/sessions/:id/complete`）は、金額の無い人なら単価を店の config から取る（以前は端末の単価を使い、その端末が単価を持たないと在庫金額が記録されない）。応答の `totalValue` は null にする。
  - `DELETE /history/:key`・`/orders/:id`・`/movements/:id` は `stock.discard`（棚卸・発注を破棄する・戻す）を要求。orders / movements の削除は App から呼ばれていない。
- **残り → 同日対応**: ルーム（DO）のホストへの単価は v0.152.9 で、ロック済み履歴の書き換えは v0.152.7 で塞いだ（session-log 参照）。
- **影響範囲 / 実装状況**: 実装済み（v0.152.5）。`worker/src/moneyGuard.js`（新規）、`worker/src/index.js`、`storeHandler.js`（`handleHistoryGetOne`、`handleStoreCreate` 削除）、
  App の未使用 `createStore` 削除。テスト `worker/test/staffMoney.test.js`（修正前のコードで 7/8 失敗を確認）。docs: api-design / security-review / spec / SEC-005。
- **PM判断**: ⬜未トリアージ

## 2026-10-07: スタッフごとのログイン（管理者・招待・役割と足し引き・ログイン中）設計たたき台（提案元: User相談 / Claude Code）

- **概要**: 今の「1店舗1ログイン＋端末名」を、**管理者とスタッフが本人としてログインする**形にする。
  招待（URL／QR・1人ずつ・10分・1回きり）→ スタッフが名前と暗証番号を入れる → 管理者が承認。
  権限は **役割3つ（アルバイト・社員・管理者）＋人ごとの足し引き5つ**。サーバー（Worker）でも必ず確かめる。
  「誰が」の記録（タスク・セッション・変更履歴）を端末名から本人へ置き換え、ログイン中の表示と見守りの情報は管理者だけに見せる。
- **背景・根拠**（User相談 2026-10-07）:
  - 店のスタッフがいつでもログインでき、タスクを登録できる。誰が登録し、誰が完了させるか（全員・誰でも・特定の人・未定）。
  - セッションの履歴に「誰が始めたか」。誰がログイン中か。誰がログインできるかは管理者が決める。
  - アルバイトに発注セッションを始めさせるだけ、社員にはある程度の権限、のように人で変えたい。
  - 細かいチェック項目の羅列は設定ミスと「なぜできないの」を生むので避け、役割で中身を決めて例外だけ切り替える（User合意）。
  - 呼び名は「管理者」。今の「ホスト」（ルームを作った人）と混ぜない。個人店と企業（多店舗）の違いは別途詰める（`enterprise-design.md`）。

### 1. 人と役割

| 役割 | 既定でできること |
|---|---|
| アルバイト | 棚卸に参加して数える・タスクの完了・発注の下書き（数を入れる） |
| 社員 | アルバイトのすべて＋棚卸・発注の開始と完了・タスクの作成・発注の書き出し |
| 管理者 | 社員のすべて＋品目マスタ（追加・変更・取込・削除）・並び替え・発注の設定・スタッフの管理・見守りの情報 |

- **オーナー**＝店を登録した人。管理者の1人で、外せない・消せない（全員が権限を外して誰も入れなくなるのを防ぐ）。
- **足し引き（人ごと・5つ）**: 発注を始める／発注を確定・書き出す／棚卸を始める・完了する／タスクを作る／品目を編集する。
  例: アルバイトに「発注を始める」だけ足す。スタッフ一覧では役割と違う人に印を付ける。

|---|:-:|:-:|:-:|

| 品目の削除・取込・全品目の削除 | － | － | ○ |

### 2. 招待とログイン

- **1人ずつの招待**: 管理者が名前と役割を決めて発行 → URL と QR（中身は同じ URL）。**1回使ったら無効・10分で無効**（User決定 2026-10-07）。
  その場で読み取ってもらう前提。間に合わなければ発行し直す。発行した招待は一覧から取り消せる。
- **店共通の QR は作らない**（User決定 2026-10-07）。招待は1人ずつだけ。
- **承認**: 登録されたら管理者に通知（Push）。承認されるまで何もできない。URL が漏れても「承認待ち」が届くだけで済む。
- **ログイン**: 名前を選ぶ＋**6桁の暗証番号**（User決定 2026-10-07。100万通り）。一度ログインした端末は覚える。共有端末は名前を選んで暗証番号で切り替え。
  **スタッフ自身のスマホからのログインも許す**（User決定）ので、店の外から試される前提で守る:
  5回まちがえたら15分止める（端末×その人の単位。人ごとに丸ごと止めると、いたずらで本人が入れなくなる）／
  123456・000000 のような番号は登録させない／管理者が解除と暗証番号の再設定をできる。
- **停止**: 管理者がスタッフを停止すると、その人のトークンを即座に無効化（以降の通信はすべて 401）。
- **削除**（User決定 2026-10-07）: 「削除済み」にする。ログインできなくし暗証番号も消すが、その人がやった記録
  （数えた・発注した・タスクを完了した）は残し「山田（削除済み）」と出す。残すのは名前だけ（プライバシーポリシーに明記）。

### 3. 「誰が」の記録

- タスク: 作った人・担当（全員＝一人ひとりが完了の印／誰でも＝誰か1人で完了／特定の人／未定）・完了した人と時刻。
- セッション: 開始した人・参加した人・完了した人。変更履歴（auditLog）の enteredBy を本人に。
- **全員に見える**: 仕事の記録（タスクの作成者・担当・完了者、セッションを誰が始めたか）。
- **管理者だけ**: ログイン中か、ログインの履歴、作業にかかった時間、人ごとの集計。

### 4. ログイン中（presence）

- アプリを開いている間、店舗単位の Durable Object と WebSocket でつなぎ、ハートビートで在席を判定（ゲームと同じ考え方）。
  操作していなくても画面を開いていれば「🟢 いま開いている」。画面を消す・別アプリに切り替えると 30〜60秒でオフライン →「最後に開いたのは10分前」。
- DO は Hibernation API で、つないでいる間の費用を抑える。見えるのは管理者だけ。スタッフには「管理者から在席が見えます」と伝える。

### 5. データ（案）

- `staff`（id, shop_code, name, role, grants_json, pin_hash, status: pending/active/stopped, created_at, approved_by, last_seen_at）
- `staff_invites`（token_hash, shop_code, name, role, kind: single/shared, expires_at, used_at, created_by）
- `auth_tokens` に staff_id を足す（NULL＝今の店舗ログイン＝オーナー）。権限の判定はトークン → staff → role＋grants。
- 既存データの移行: 今の店舗ログインはオーナーとして扱う。端末名だけの過去の記録は「名前（端末）」のまま残し、本人へは結び付けない。

## 2026-09-24: 初回棚卸からの仮の発注基準（フェルミ推定）で「発注点をまとめて設定」を置き換える（提案元: User相談 / Claude Code）

- **概要**: 実績（消費推定・在庫の最小値）がまだ無い品目に、**直近の棚卸数量と店舗の仮定3つ**
  （届くまでの日数・余裕の日数・何日分置いているか）から「仮」の発注点と補充目標を出す。
  仕入れカード在庫タブの「🎯 発注点をまとめて設定」をこの画面に差し替える。**v0.108.0 で実装済み**（下記「実装メモ」）。
- **User決定（2026-09-24）**:
  1. **AIは使わない**（元案の商品特性解析は外す。数字に効く値はどれもAIで確定できないため）
  2. **推奨発注数は入数の切り上げ**にする（D4 の「切り捨て」を置き換える。下記 §4）
- **背景・根拠**: 今は棚卸2回以上ないと目安が出ず、それまでは発注点を人が1品ずつ入れる必要がある
  （D-024 の部分利用ユーザーほど長く空欄）。一方、実績が貯まった後の層（`impliedConsumption` /
  `orderLearning` / `replenishTarget` の優先順位）は既にあるので、**足りないのは実績ゼロ期間の
  仮の値だけ**。元案（ChatGPT作成）の §7 実績補正・§8 状態管理は既存の `source` でほぼ満たせる。

### 1. 推定の限界（先に明記）

- 使える事実は**その品目の棚卸数量1つだけ**。展開すると
  `発注点 = 在庫 ÷ 在庫日数 × (届くまで + 余裕)` で、**中身はほぼ「在庫日数」という仮定そのもの**。
- 棚卸は発注直前に行うことが多く、そのとき在庫はサイクルの底 → **使用量を少なく見積もる**。
  まとめ買い品（米・油の買い置き）は逆に**多く見積もる**。
- 在庫0の品目は推定できない（空欄のまま）。
- 参考: 既定値（週1発注・届くまで1日・余裕1日）では補充目標が「在庫×1.8」になり、
  **数字自体は今の「発注点×2」と大差ない**。得るものは「人が1品ずつ入れなくてよい」ことと
  「仮定が意味のある言葉で直せる」こと。精度向上を期待する機能ではない。
- よって表示は常に **「仮」バッジ＋式** を出し、確定値のように見せない。

### 2. 計算（純関数・`services/` に追加）

| 記号 | 意味 | 持ち方 |
|---|---|---|
| Q | 直近の棚卸数量（在庫観測の最新） | 既存 `stockObservations` |
| I | 発注間隔（日） | 既存 `orderIntervalDays(orderSchedules)`（曜日の最大ギャップ＝金→月の空きも含む） |
| L | 発注から届くまで（日） | **新規**・店舗1つ。既定 1 |
| S | 余裕の日数（安全在庫） | **新規**・店舗1つ。既定 1 |
| D | 何日分置いているか | **新規**・店舗の既定＋ジャンル別の上書き。既定 `round(I/2 + S)`（週1なら5） |

- 推定日消費 `d = Q ÷ D`（Q≤0 または D≤0 → null）
- 仮の発注点 `ceil(d × (L + S))`
- 仮の補充目標 `ceil(d × (I + L + S))`
- D の既定根拠: 定期発注の店で任意の時点の在庫は平均「発注間隔の半分＋余裕」。発注頻度から出せるので AI は不要。

### 3. 既存の優先順位への差し込み（状態＝既存の `source`）

- `reorderSuggestion`: `consumption` → `stocktakeMin` → **`assumed`（新）** → null
- `replenishTarget`: `manual` → `par` → `consumption` → **`assumed`（新）** → `reorder`（×2）
- 元案 §8 の状態との対応: 仮設定＝`assumed` ／ 実績反映＝`stocktakeMin`・`reorder` ／
  需要ベース＝`consumption`・`par` ／ 手動＝`manual`（`reorderPoints`/`replenishTargets` に数値がある品目）
- **仮の値は保存しない（その場で計算する）**。保存すると実績が貯まっても古い仮の数字が
  「手動」扱いで残り、自動で卒業できない。保存するのは人が直した値だけ → 手動は上書きされない、
  実績が貯まれば仮は自然に消える、の両方が既存の仕組みのまま成り立つ。
- **有効化は店舗単位**: 仮定（L/S/D）を一度保存した店舗だけ `assumed` を使う。未設定の店は今と同じ挙動。

## 2026-09-09: Riveを公開面で動かすためCSPに`'wasm-unsafe-eval'`を足す（実装済み・User指示のRive導入に伴う／UI-005）

**概要**

ランタイム（JS 195KB・WASM 2.05MB）と `.riv` をプリキャッシュに載せず、初回取得→以後
キャッシュ（CacheFirst）にする。演出そのもの・素材は `UI-004`（Codex）の範囲で、本件は前提だけ。

**背景・根拠**
- Chromium系はChrome 97以降、WASMの実体化に `'wasm-unsafe-eval'` か `'unsafe-eval'` を要求する。

- `'unsafe-eval'`（JSのeval全許可）ではなく `'wasm-unsafe-eval'` に限定する。後者はWASMの

- キャッシュ方針は「演出を見ない人に払わせない」を優先。WASM 2MBはプリキャッシュに載せると
  初回インストールが2.7MB→4.8MB以上になり、workboxの既定上限(2MB)も超える。
  逆にrun-time cacheが無いと、電波の悪い店で毎回失敗する。両者の間を取る。

**影響範囲 / 実装状況**
- `app/public/_headers`: `script-src` のみ変更。他directiveは無変更。
- `app/vite.config.js`: `globIgnores: ['**/riveRuntime-*.js']` と runtimeCaching `rive-runtime`
  （CacheFirst・1年・maxEntries 8）。対象は `riveRuntime-*.js` / `*.wasm` / `*.riv`。
- 検証: 一時的な動的importでビルドし、プリキャッシュが 17 → 19 entries（+3KB＝`RiveCanvas`の
  js/cssのみ）でランタイムJS・WASMが載らないことを確認して元に戻した。詳細は `UI-005.md`。
- 画面・業務データ・同期・認可・app versionは無変更。

**PM判断**: ⬜ (1) CSPを1段緩めることの可否（`'wasm-unsafe-eval'` 限定・`'unsafe-eval'` は入れない）。
Web release gate（`WEB-01`〜`WEB-10`）にCSPの項があるなら、その再確認要否も。
(2) 製品画面へ組み込むときの条件として「Riveが落ちても画面が使える（静的アイコンへfallback）」を

**概要**
振り分けホイールを帯（band）へ畳んでいる間も、中央カードの件数バッジを押して
「振り分け済み」を開けるようにする。押しても面積は広げず、帯のまま保つ。

**背景・根拠**
畳んだ状態は「品目を一覧へ入れている最中」で、いま入れている分類先に何件入ったかを
確かめたくなるのはまさにその最中である。従来は扇（fan）が0.6以下だとカード全体の
pointer-eventsを落としていたため、件数を押すにはまずホイールを開き、開き終わるのを
待ってからもう一度押す、という二度手間が要った。開く操作は「分類先を変えたい時」に
必要なのであって、件数の確認まで同じ段階に隠すのは畳んでいる意味を失わせている。
一方、畳んだ状態では周りのカードが中央へ重なって見えないため、カードを一律に
押せるようにすると、見えないカードを踏んで意図しない分類先へ回ってしまう。
そこで**中央の1枚だけ**を常時押せる形にした。

**影響範囲 / 実装状況**
- `AxisAssignFocus.vue`: 中央カードの`pointerEvents`をfanに連動させず常時`auto`にした。
  非中央カードは従来どおりfan>0.6でのみ押せる。
- `stopWheelForControl()`は畳んでいる時に`open`へ広げない。件数を押しても帯のままで、
  シートを閉じた後の品目一覧の位置が変わらない。
- 帯の中では件数バッジのタップ領域を44pxへ広げ、カードのタップ（＝ホイールを開く）と
  押し分けられるようにした（開いている時の見た目は変更しない）。
- 分類先の選択・保存先・循環順・reduced motion・レール（＋⚙🗑）の扱いは変更なし。
  レールは畳んでいる間`inert`のまま。
- 自動test（帯のまま件数から開けること、押せる相手が中央の1枚に限られること）追加。
- **追補**: pointer-eventsを開けるだけでは実機で開かなかったため、(a)畳みきったら中央以外の
  カードをDOMごと描かない、(b)`click`だけでなく`pointerup`でも件数の押下を成立させる、
  の2点を足した。3Dで完全に重なったカードやPointer Captureが絡むと、端末によっては
  clickのtargetがstageへ置き換わり、件数buttonまで届かないため。

**PM判断**: ⬜ 畳んだ状態で押せる操作を「件数だけ」に留めるか、レール（＋⚙🗑）まで
広げるか。今回はUser指示により件数のみ。

## 2026-09-02 — 数値が読めない行を丸ごと捨てている（**2026-09-03 実装済み**・PM判断待ち）

**概要**
「品目名が空だったり数値が文字列だったりすると、その行は全部除外されるのか」という
Userの問いから実挙動を測った。**行が丸ごと落ちる。** しかも扱いが3通りに割れていて、
一貫していない。

**実測（`parseItemCSV` → `buildImportPlan`）**

| 入力 | 結果 | 数え方 |
|---|---|---|
| 品目名が空 | 行を除外 | skipped |
| 単価が読めない（`約980円`） | **行を丸ごと除外** | errors |
| 列数がヘッダと不一致 | **行を丸ごと除外** | errors |
| 入数・前月実績が文字（`S` `前月なし`） | **そのまま取り込む** | 数えない |

```
  鶏もも,kg,約980円,精肉,,102,,8,1
    → 3行目 単価「約980円」は数値として読めません
    → 「鶏もも」ごと取り込まれない（品目名・単位・カテゴリ・コードは全部正常）
```

原因は `_collectRows` の `if (errors.length) { parsed.errors.push(...); continue }`。
`_buildRow` が数値検証するのは `price` / `categoryCode` / `reorderPoint` だけなので、
同じ「数値の欄に文字」でも**単価は品目を消し、入数は黙って通る**。

**経緯**
IMPORT-001 で直したのは「読めない数値を*既存値の維持として黙って扱っていた*」こと。

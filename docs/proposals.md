# セッション提案箱（PMトリアージ用）

最終更新: 2026-08-27
位置づけ: 各実装/戦略セッションから **PMセッションへの「提案・設計判断・要検討」の集約箱**。
`intake-reviews.md`（PM→実装のレビュー＝下り）に対して、これは **実装/戦略→PM（提案＝上り）**。
PMがトリアージし、採否と恒久docsへの反映先を「PM判断」欄に記入する。

## 使い方

- 新規提案は**日付見出しで先頭に追記**する（新しいものが上）。
- 1提案 = 概要 / 背景・根拠 / 影響範囲・実装状況 / PM判断。
- **PM判断**の状態: ⬜未トリアージ ｜ ✅採用（→反映先ファイル） ｜ 🕓保留 ｜ ❌却下。
- PMが恒久docs（strategy / roadmap / project-status / pricing-strategy / ordering-analytics-design 等）へ
  反映したら、ここのエントリは削除せず「✅採用（→ファイル名）」に落として記録として残す。
- 実装済みの提案でも、**設計判断としてdocsに残すべきか**の判断はPMが行う（実装＝合意ではない）。

### テンプレート（コピーして先頭に貼る）

- `## YYYY-MM-DD: <タイトル>（提案元: <領域/セッション>）`
- **概要**: 何を提案するか（1〜2行）
- **背景・根拠**: なぜそうすべきか
- **影響範囲 / 実装状況**: 触る場所・すでに実装したか
- **PM判断**: ⬜未トリアージ

**概要**

**影響範囲・実装状況**

- 検証: worker 592 / app 1443 passed、app build 成功。**実機・実ブラウザは未確認**。

**PM判断が要る点** ⬜
1. **閲覧期間3日のままでよいか**。訂正期間（`CORRECTION_DAYS`）に合わせた値だが、
   両者は本来別の概念。本部・会計士へ渡す用途なら3日は短い。
   決めるなら `RESULT_WINDOW_DAYS` を訂正期間から独立させる（コード上は既に独立している）。

   金額の動きが大きい品目 上位5）／担当者別（操作数・品目数・重複数）。
   **合計金額の隣に「単価未設定で金額に入っていない品目数」を必ず出す**。
   これを黙らせると、一部しか計上されていない数字を正しい在庫金額として読ませてしまう。
   前回比は**両方に金額がある品目だけ**を比べる（片方が単価未設定の品目を0扱いすると、
   単価の入れ忘れが「在庫が消えた」差分として出る）。

本件はそれに反するが、User の実運用が先に来たため実装した。取り込み可否は PM 判断。

## 2026-08-27: 品目の非表示に「全スワイプ」を足し、その場合だけ確認を飛ばす（提案元: User指示 / Claude Code）

- **概要**: `InventoryTable` の手動非表示（左スワイプ）を2段階にした。
  - **浅いスワイプ** … 「非表示」ボタンが出て止まる → 押すと確認ダイアログ（**従来どおり**）
  - **全スワイプ** … 行の半分以上まで引いて離す → **確認を挟まずその場で非表示**
- **背景・根拠**: User指示。非表示は破壊的ではなく、一覧上部の
  「手動非表示 N件 ・ タップで管理」からいつでも戻せる。まとめて隠したいときに
  ダイアログの往復だけが残るのは割に合わない。一方で浅いスワイプまで無確認にすると、
  縦スクロールの巻き添えで品目が消えるので、**引き切った操作だけ**を無確認にした。
- **影響範囲 / 実装状況**（実装済み）:
  - 閾値は `max(160px, 行幅 × 0.5)`。行幅が測れない環境でも 160px で成立する。
    抵抗（ラバーバンド）を掛け始める位置を閾値より手前にしないよう `dragMax` に下限を入れた
    （従来は 96px から抵抗が始まり、引き切るのに実質 300px 以上の指の移動が必要だった）。
  - アクションは引いた分だけ広がり、閾値を越えると文言が **「離すと非表示」** に変わる。
    隠しジェスチャなので、指を離す前に結果が読めるようにした。
  - **色も引いた量に比例して灰（`#64748b`）→ 赤（`#dc2626`）へ寄せる**（User指示・追加）。
    文言だけだと「あとどれだけ引けば確定するか」が分からないため、途中経過を色で出す。
    閾値ちょうどで赤になり、さらに白の内側リングを足して「引き切った」ことを二重に示す。
    背景を inline style が持つので、押下feedbackは背景色ではなく `filter: brightness()` に変えた。
    白文字とのコントラストは灰 4.8:1 / 中間 5.8:1 / 赤 4.8:1 で、いずれも AA（4.5:1）を満たす。
  - 確定は同期的に `hide-item` を emit するだけで、退出アニメーションは持たない。
    親が `hiddenItems` を更新した時点で行が一覧から外れるため、アニメーションを持たせると
    「消えたはずの行」を掴んだままになりうる。親が受け取らなければ元位置へ戻る。
  - 確定後は `App.vue` 側の既存トースト「『◯◯』を一覧から非表示にしました」が出るので、
    無確認でも何が起きたかは画面に残る。
  - ついでに `_suppressClick` を touchstart で落とすようにした。全スワイプでは行が消えるため
    touchend 後の click がどこにも届かず抑止が消費されない経路ができ、**次の1タップが
    無視される**。従来からある「開いた行をタップして閉じた」経路でも同じ取りこぼしがあった。
  - `InventoryTable.swipeHide.test.js` を追加（5件）。全スワイプの無確認確定、浅いスワイプの
    確認維持、途中で戻す、縦スクロール、ゲスト不可。修正前は1件目だけが失敗することを確認済み。
- **未決 / 検討事項**:
  - 実機での閾値の感触（`0.5` と 160px）は未検証。深すぎ/浅すぎならここだけ調整する。
  - `AxisAssignFocus` 側の非表示は別UI（ボタン）なので今回は触っていない。
  - 取り消しは管理シート（「手動非表示 N件」）のみ。トーストに「元に戻す」を付けるかは
    PM判断（今回のscope外）。
- **PM判断**: ⬜未トリアージ

## 2026-08-26: 操作ログ（変更履歴）を D1 に持つ ②（提案元: User承認 / Claude Code）

- **背景**: 商業利用では「誰が・何を・いつ変えたか」を後から辿れることに価値がある
  （数字が合わなかったときに誰の入力を見ればよいか）。
  それまでの置き場所はどちらも記録の正本になり得なかった:
  - Durable Object … ルームの生存期間に縛られ、新しいセッションの開始で消える。
    そもそも DO は「その場の調整役」で system of record ではない
  - 端末の localStorage … 1台に依存し、完了前に端末を失えば記録ごと消える
  完了後は `snapshot_json` で D1 に残るが、**進行中は残らない**。
- **User判断**: 商業用途なら②が望ましい。①を土台として先に入れ、②は承認後（本セッションで承認）。
- **実装（v0.85.0）**:
  - **migration `0017_session_audit.sql`**: 1操作＝1行。`(shop_code, id)` を PK にして
    `INSERT OR IGNORE` で**再送しても重複しない**。索引はセッション単位と品目単位の2本。
    削除済みアカウントへ書かせないトリガは 0011/0012/0015/0016 と同じ方針。
    **新規table追加のみでロールバック可**（0012 のような不可逆点ではない）。
  - Worker: `POST/GET /store/:code/sessions/:id/audit`（要認証）。
    他店舗のセッションへは書けない（404/409）。1要求 200件上限。
  - Client: `composables/useAuditSync.js`。**追記専用**なので pendingSaves の
    「最新が勝つ」キューには載せず別に持つ。3秒まとめ or 200件で送信、
    失敗はキューに残して再送、localStorage で再読込をまたぐ。
    D1 への記録は1端末が代表（ソロは自分・ルームはホスト。ゲストは認証を持たない）。
  - 再開・起動時に `GET .../audit` を統合する。**これが「別の端末が入っても確認できる」経路。**
- **fail-soft の設計**: table が無い環境（0017 未適用）でも
  読み出しは空配列、追記は 503 retryable を返して**棚卸自体は止めない**。
  完了スナップショットが履歴を D1 へ運ぶので、送り切れなくても記録は残る。
- **未実施（承認が要る）**:
  - **本番 D1 への 0017 適用**（`WEB-04` に合流。0010〜0017 の順で適用）

## 2026-08-27: 戻るの受け皿を切らさない（データ管理の戻るでアプリを離れる不具合）（提案元: User報告 / Claude Code）

- **報告（User）**: データ管理で戻るを押すと、ホーム（セッション・ダッシュボード）へ戻らず
  **アプリ自体から離れてしまう**。
- **原因**: このアプリはURLルーティングを持たず、端末の戻るは
  `history.pushState` で前に1枚積んだ**受け皿（sentinel）**で受けている。
  `_onBrowserBack()` は「1枚閉じたら積み直す」だが、**ランディングでは閉じるものが無く
  積み直さない**（次の戻るでアプリを離れる＝意図どおり）。
  問題は、その状態から**画面を進めても積み直していなかった**こと。
  受け皿が無いまま進むので、進んだ先での戻るが1回でアプリを離れる。
  - 再現: `ホーム → 戻る（ランディング）→ 戻る（受け皿を使い切る）→ ホームへ進む
    → データ管理 → 戻る` で離脱。データ管理固有ではなく、**どの画面でも起きる**。
  - 前進では sentinel を積まない設計だったため、「戻る→進む」を1往復した時点で
    以後ずっと受け皿が無い状態が続いていた。
- **修正**（実装済み）:
  - `App.vue`: `_backArmed`（受け皿が前に居るか）を持つ。`_pushBackSentinel()` で true、
    `_onBrowserBack()` の冒頭で false。`currentView` を watch し、
    **受け皿が無いままランディング以外へ進んだら積み直す**。
  - ランディング自体では積まない。ランディングでの戻る＝アプリを離れる、は変えない。

  この画面にだけ積み直しの機会が無かった（他画面は view が変わるので自然に直っていた）。
  - 受け皿の有無を `_backArmed`（こちらの記録）だけでなく **`history.state.pwaLayer`
    （ブラウザの実態）**でも見るようにした。「積んだつもりで実は無い」を検出できる。
    プログラムから積んだ履歴を戻るが読み飛ばすブラウザ実装への備えでもある。
  - 積み直しの引き金に **pointerdown / keydown**（capture + passive）を足した。
    段が進むのは必ず操作の直後なので、view を持たない画面内の段もこれで拾える。
    操作を伴う履歴として積めるため、読み飛ばし対策にもなる。
- **残る限界 / 未決**:
  - 積み直しの引き金は `currentView` と操作。**ランディングから直接開くモーダル**があると、
    受け皿が無い状態でそのモーダルを開いた場合に戻るで離脱しうる。
    現状のランディングは「はじめる」で view が変わる導線しか無いので実害は無いが、
    ランディングにモーダルを足すときは同じ手当てが要る。
  - jsdom は `popstate` を投げても履歴の位置が動かないため、
    **実ブラウザの「受け皿が無ければ離れる」はテストで再現できない**。
    test は「積み直しが走ったか」で代替している。実機確認が要る。
  - 恒久的にはURLルーティング（hash か History API）へ移すのが本筋。
    sentinel 方式は画面の段と履歴が別物のままで、この種の穴が残りやすい。

- A7 v0.68.0 で入れた入庫/出庫の表化は土台として活かす。

### B. 統合カード

- タブ順は業務の流れ（在庫 → 発注 → 入庫 → 出庫）、既定タブは**在庫**。
- **発注タブは既存の発注セッションを開く入口**にする。カード内に軽い発注記録を別に作ると
  「どちらが正か分からない」2経路になるため作らない。
- **発注レコードと入出庫レコードは分けたまま**にする。統合すると
  ①発注した瞬間に理論在庫が増える ②発注差異（頼んだ数と届いた数）が消える
  ③LOT数とバラが同じ `qty` に混ざる ④発注提案の学習母集団（`stock`/`postStock`）が壊れる。
- 入庫タブ先頭に「未反映の発注」を常設し、`deliveryLinesFromOrder` でプリフィル。
  「発注12 → 実際10」の差異を表示する。
- 発注点・発注日締切はヘッダーの ⚙ から（`OrderScheduleModal` を流用）。
- 出庫はβバッジを維持し既定タブから外す（`web-release-readiness.md` の
  「出庫は主要導線外」を満たすため。**文言はCodexレビュー対象**）。

### C. 発注数の決め方

- モードA=発注数を直接入力 / モードB=在庫を入力して不足分を自動算出、の**両方**を用意する。
- **在庫入力は両モード共通で必須**。任意にすると消費推定の観測点（`stockObservations`）が
  欠け、分析の土台が崩れる。
- **「補充目標」を導入する**。発注点は「下回ったら発注する」トリガーで、そこへ戻すと
  補充直後にまた発注点を割る（＝毎回発注になる）。目標水準は別に持つ。
  - 既定は `補充目標 = 発注点 × 2`（変更可）。
  - 消費が算出できるようになったら `発注点 + 発注間隔ぶんの推定消費` へ自動で切り替え、
    切り替わったことを画面に出す。手動上書きは常に優先。
  - 適正在庫（`orderLearning.parLevel`）が貯まっていればそれを優先する。
- 自動算出後も人が必ず直せる。学習は**直した後の値**で回す。

### D. 消費推定と学習（部分利用ファーストで優先度を組み替え）

1. **発注点の初期値提案**（棚卸の数量から提案・一括設定）← 部分利用では学習が貯まらないため最優先
2. **発注日をまたぐ区間の除外**: 区間が `config.orderSchedule.days` の発注日をまたぐのに
   入庫記録が0件なら、記録外の納品があったとみなして学習から外す。
   現状 `impliedConsumption` はマイナス消費だけを `flagged` で除外しており、
   **在庫が減ってさえいれば過小評価がそのまま通る**（前回10・未記録入庫20・今回5 → 消費5と誤認）。
   過小評価は適正在庫を低くし、欠品につながる。追加入力なしで判定できる。
3. **推定の検証**（推定した消費 vs 実際の棚卸差を見せる）← 精度を語る前提
4. 暦要因（連休・祝日）を推奨に効かせる。`demandFactors` は現状カレンダー表示専用で、
   コメントどおり「効かせるは別レイヤー」。**係数として掛け、根拠を必ず表示**する
5. 天気（`useWeather` は取得済み・推奨に未接続）
6. 月・第○週・季節は**1年分貯まるまで着手しない**（月別は1品目あたり年1サンプル）
- 算出できないときは理由を出して**出さない**方針を維持する（`analysisCapability` の延長）。

- **影響範囲 / 実装状況**: **未実装**（Aから着手）。Worker / D1 / migration の変更は想定していない。
  `InventoryTable` は棚卸の主経路・発注・完了済み詳細・品目マスタ確認が共有するため、
  変更のたびに4画面の回帰確認が必要。

  登録時に業種・使用目的の簡易アンケートを取る。**実装時期は未定**で、本エントリは設計の先行確定のみ。
- **背景・根拠**:
  - 現在の識別子は `shop_code + 4桁PIN` だけで、**PINを失うと店舗データへの復旧手段が一切ない**
    （`handleLogin` はPIN照合のみ、`stores.pin_hash` を再設定する経路が存在しない）。
    公開後にサポート負荷として跳ね返る性質の欠落であり、動機は正当。
  - アンケートは業種別の初期辞書・品目テンプレの精度、および機能／料金の優先順位判断に効く。

### 設計判断（PMトリアージ希望）

**1. メールを identity にせず「復旧用の連絡先」に留める（最重要）**

`enterprise-design.md` §9.1 は「店舗＝共有アカウント（`shop_code + PIN` を知る全員が同一識別）」を
*業種特性に合った良い割り切り*として明示採用し、§9.2 でメール認証は **org_admins（本部層）** に置いている
（`org_admins` は `email` を主キーに持つ）。店舗レイヤーの identity をメールへ移すと、この2階層設計と衝突する。
飲食店の現場は複数スタッフが同一店舗コードで入る運用のため、メール＝ログインIDにすると運用も壊れる。

→ `stores` へ復旧用メール（任意・確認済みフラグ付き）を足すだけに留め、**ログインは従来どおり
`shop_code + PIN`** とする。これなら enterprise 設計と矛盾せず、将来 org 層を載せる余地も残る。

**2. PIN復旧は「ログイン相当」であり、単一ホストセッションの副作用を伴う**

`authHandler.js:142` はログイン成功時に `DELETE FROM auth_tokens WHERE shop_code = ?` で他端末を全失効させる。
復旧を同じ扱いにすると**棚卸作業中の他端末が落ちる**。乗っ取り対策としては全失効が正しいので、
挙動は維持したうえでUIに「他の端末はログアウトされます」を明示する。

**3. 4桁PINとメール復旧の強度差を埋める条件**

PINは10,000通りで、現在は15分5回のレート制限（`shop_code` 単位）が実質的な防御。メール到達だけでPINを
再設定できるようにすると、**アカウントの実強度＝メールアカウントの強度**になる。一般的な設計だが、
以下を満たさないと `SEC-001`〜`SEC-004` で閉じた認可境界を迂回される。

- 復旧トークンは**単回使用・短命（15〜30分）・ハッシュ化して保存**
- 復旧完了時に **auth_tokens とホストトークンを全失効**
- 復旧要求のレート制限（メール単位＋IP単位。既存 `ip_attempts` を流用可）
- **列挙対策**: 復旧要求の応答は、メールの登録有無にかかわらず常に同一にする。
  メールから店舗コードを引ける導線を作ると、`shop_code` を知らない攻撃者が対象を特定できるようになる
- **未確認メールでは復旧不可**（確認済みフラグ必須）。登録直後の確認メールで確定させる

復旧方式は User 未決。比較は下表（`SEC-006` の脅威モデルと合わせて確定させたい）。

| 方式 | 利点 | 弱点 | 備考 |
|---|---|---|---|
| メールに復旧リンク | 実装が単純。桁数の総当たりが無い | メールクライアントのプリフェッチで単回トークンが消費され得る | 消費はGET不使用（確認画面＋POST）で回避 |
| メールに数字コード | スマホでアプリ内完結。端末を移らない | コード総当たりの余地。試行回数制限が必須 | 6桁＋5回上限＋短命なら実用強度 |
| 併用 | 双方の導線を吸収 | 実装・テスト量が2倍 | 初版では非推奨 |

**4. 削除範囲の変更（`PLAY-001` の承認済み data map に影響）**

`accountDeletion.js` は現在13グループを物理削除し `stores` を匿名 tombstone 化する。メール・復旧トークン・
アンケート回答を**追加列挙**し、`0011` と同型の active-insert トリガを新テーブルにも付ける必要がある。

新論点: **7日 tombstone の間に同じメールで再登録できるか**。tombstone に生メールを残すと「削除したのに
保持されている」ことになり、消すと再登録時の重複検知ができない。→ **ハッシュのみ7日保持**を推奨する。

**5. アンケートは任意・目的限定**

業種・使用目的も Data Safety の申告対象。必須にすると登録離脱を招き、Play の「機能に不要なデータ収集」
観点でも不利。→ **スキップ可**とし、目的（初期テンプレの出し分け・改善統計）を画面に明示、
個人特定に使わない旨を privacy へ記載する。

**6. メール配信基盤の選定が前提作業**

現在バックエンドに送信経路が一切ない（`worker/src` に該当実装なし）。構成上は Cloudflare Email Service
（Email Sending）が最も自然（既に全面 Cloudflare）。**送信ドメインの確保と SPF/DKIM/DMARC 設定**が
先行タスクになるため、canonical host（`DS-08`）の決定と同じタイミングで決めるのが効率的。

- **影響範囲 / 実装状況**: **実装なし（設計提案のみ）**。実装する場合に触る範囲:
  - migration 新規（`stores.recovery_email` / `recovery_email_verified_at` / 復旧トークン表 / アンケート回答表）
  - `authHandler.js`（register拡張、復旧3経路＝要求・検証・PIN再設定）、`accountDeletion.js`、トリガ追加
  - Data Safety 台帳・申告draft（`Personal info > Email address` が**アカウント連結**で追加され、
    `data-safety-form-draft.md` の前提「アカウントに紐づく個人情報なし」が崩れる）
  - privacy §2「取得しない情報」／§4 外部送信（配信基盤が新規委託先）／§5／§6 保存期間
  - terms 第6条3・第11条3（連絡先を持つため「掲示」→「利用者へ通知」が履行可能になる）
  - スプリント凍結（2026-07-27〜08-08）は Play 要件外の新機能を停止対象としており、
    **実装着手は 8/8 以降、または凍結解除の User 判断が必要**
- **PM判断**: ⬜未トリアージ

## 2026-07-21: 入出庫（movements）を D1 永続化・端末間で揃える（提案元: 入出庫セッション）

- **概要**: これまで localStorage 専用だった入出庫レコードを、発注・棚卸と同様に **D1 を正**として
  永続化。保存時 POST・開始/表示時ロードの「非リアルタイム同期」で、端末をまたいで入出庫が見え、
  キャッシュ削除・端末紛失でも消えないようにした。
- **背景・根拠**: 発注・棚卸は D1 化済みなのに入出庫だけローカル専用で、①別端末で入出庫が存在しない
  ②「発注はD1・入庫はローカル」で理論在庫/発注→入庫反映が端末間で食い違う、という非対称があった。
  加えて、発注削除がローカルのみで D1 から復活し「未反映の入庫」に再表示される不具合の同型リスクが
  入出庫にも生じるため（D1化するなら削除もD1連動が必須）、あわせて対処した。
- **設計判断**: 入出庫は「確定済み記録の追記ログ」で複数人同時編集が無いため、棚卸・発注のような
  **WebSocket リアルタイム同期は採用せず**、発注レコードと同じ「保存時POST＋開始時ロード（id重複排除で冪等）」に
  留めた（DO 併設は過剰と判断）。
- **影響範囲 / 実装状況**: 実装済み。
  - 追加: マイグレーション `0010_movements.sql`（`movements`/`movement_lines`）、

    `useMovements.applyRemoteMovements`。
  - 配線: `MovementPage.onSave` で保存後 POST、`App._pullMovements` を認証後/入出庫ページ表示時にロード、
    `HistoryCalendar.onDeleteMove` で D1 からも削除。

  「削除直後のUndoトースト」を将来入れる余地あり（別提案化の候補・本セッションで方針保留）。
- **PM判断**: ✅採用（2026-07-21 PMセッション・条件付き）
  - 採用理由: Wave 2.5 #2（料金戦略「無料の床」の前提）そのもの。「追記ログに

    テナント境界が破れる。修正まで「完了」扱いにしない（→ `intake-reviews.md`）。

- **影響範囲 / 実装状況**: 未実装（提案のみ）。R3-01 の即時修正（normalizeConfig に orderSchedule 追加＋
  テスト）は完了済み。本提案はその再発防止レイヤー。
- **PM判断**: ✅採用（2026-07-20 PMセッション・**案1「守りのテスト＋共有キー定数」を採用**）
  - 理由: 同型事故2回は構造問題。案1は低コストで「追加漏れ＝テスト即失敗」に変えられる。
    案2（正規化ロジック完全共有）はビルド構成を跨ぐ複雑さに見合う破綻がまだ無いので現時点は見送り

## 2026-07-17: 発注点は「人間が決める床＋データの推奨」の二段構え（提案元: カード/入出庫セッション）

- **概要**: 手動発注点＝人間が決める絶対下限（床）として扱う。予測モデルは発注点/発注量の
  「推奨」を出す側で、**手動値は自動上書きしない**（タップ採用で合成。実務は `max(手動床, 推奨)` が安全側）。
- **背景・根拠**: 在庫理論では別レイヤー。
  - **発注点(ROP)**＝*いつ*頼むか＝リードタイム中の予測需要＋安全在庫
  - **発注量**＝*いくつ*頼むか＝次納品までの予測需要＋安全在庫−現在庫（曜日別・外的/内的要因はここ）
  - **安全在庫**＝*切らせない*緩衝＝需要のブレ×リードタイム×目標欠品率
  - 「これさえ守れば絶対切れない」は数学的に不可能。実装上は**サービスレベル（欠品率）で安全在庫の大きさを選ぶ**話に落ちる。
  - 発注点はリードタイム前提で意味を持つ → 他セッションの**発注スケジュール（発注曜日/締切）がリードタイム構造**、
    **需要カレンダー（祝日・給料日等）が外的要因**として噛み合う。
- **料金戦略との整合**: 手動発注点＝シンプル/データ不要＝**無料の床でも出せる**。
  予測（曜日別・外的/内的要因）の推奨＝データと計算＝**有料の差別化**。`pricing-strategy.md` の wedge と一致。
- **影響範囲 / 実装状況**: 実装済み（`5e918d6` ほか）。
  - `reorderPoints` を config フィールド化（default/serialize/assign/rename/remove/setter＋RoomDO中継。localStorage/D1/ルーム同期）
  - 「要補充」判定を `理論在庫 ≤ 発注点`（未設定は0以下）に。在庫タブのフィルタ・件数・強調が連動
  - 在庫タブの品目詳細に手動入力＋**暫定「目安」**（直近30日の平均日消費 × 発注間隔）。タップ採用・自動上書きなし
  - 暫定ヒューリスティックは需要カレンダー/曜日別モデル完成時に置換予定
- **PM判断**: ✅採用（2026-07-18 PMセッション）
  - 反映先: `ordering-analytics-design.md` §2.3（パー→発注点の二段構えとして全面更新・用語定義も同節に収録）、
    同書ヘッダの実装状況、`roadmap.md` E節。
  - 採用理由: ①在庫理論と整合（ROP/発注量/安全在庫のレイヤー分離）②「手動値を自動上書きしない」は
    本プロダクトの原則「勘を潰さず、目安を出す」と一致 ③無料の床=手動/有料=予測の切り分けが
    `pricing-strategy.md` の wedge と噛み合う。
  - 補足条件: 「絶対切らさない」は数学的に不可能のため、UI文言では「切れにくくする目安」等の
    表現を使い、保証と誤読される語（必ず・絶対）を避けること（レビュー時に確認する）。

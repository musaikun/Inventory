# セッション提案箱（PMトリアージ用）

最終更新: 2026-08-25
位置づけ: 各実装/戦略セッションから **PMセッションへの「提案・設計判断・要検討」の集約箱**。
`intake-reviews.md`（PM→実装のレビュー＝下り）に対して、これは **実装/戦略→PM（提案＝上り）**。
PMがトリアージし、採否と恒久docsへの反映先を「PM判断」欄に記入する。

## 使い方

- 新規提案は**日付見出しで先頭に追記**する（新しいものが上）。
- 1提案 = 概要 / 背景・根拠 / 影響範囲・実装状況 / PM判断。
- **PM判断**の状態: ⬜未トリアージ ｜ ✅採用（→反映先ファイル） ｜ 🕓保留 ｜ ❌却下。
- PMが恒久docs（strategy / roadmap / project-status / pricing-strategy / ordering-analytics-design 等）へ
  反映したら、ここのエントリは削除せず「✅採用（→ファイル名）」に落として記録として残す。
- 実装済みの提案でも、**設計判断としてdocsに残すべきか**の判断はPMが行う（実装＝合意ではない）。

### テンプレート（コピーして先頭に貼る）

- `## YYYY-MM-DD: <タイトル>（提案元: <領域/セッション>）`
- **概要**: 何を提案するか（1〜2行）
- **背景・根拠**: なぜそうすべきか
- **影響範囲 / 実装状況**: 触る場所・すでに実装したか
- **PM判断**: ⬜未トリアージ

## 2026-08-25: 参加者別を変更履歴の200件上限から切り離す（提案元: User報告 / Claude Code）

- **要件（User）**: 「誰が・何を・いつ入力したか」と「担当者別の入力品目一覧」を、
  各棚卸で**正確に**確認したい。
- **問題**: 参加者別は独立した記録ではなく、`buildSnapshot` が **auditLog（変更履歴）から
  品目ごとの最終更新者を逆算**して作っていた。auditLog は端末・DO とも 200件上限で
  古い方から捨てるため、**品目数が200を超えると古い品目の担当者が不明になり、
  参加者別からまるごと抜け落ちる**（530品目なら330品目ぶん）。訂正入力も1件ずつ消費するので、
  実際にはもっと早く溢れる。
- **修正**（実装済み）:
  - 担当は **在庫データが品目ごとに持つ `enteredBy` / `updatedAt` を正**とする。
    在庫側は品目ごとに1件なので、品目数がいくつでも全件に担当が付く。
    `enteredBy` を持たない古い下書きのために、auditLog からの逆算は予備として残した。
  - 参加者別の品目に **`at`（その品目を入力した時刻）** を持たせ、
    Worker の `_snapshotMeta` と `_sanitizeForGuest` を通す。詳細画面で品目ごとに時刻を出し、
    入力順に並べる。
  - 稼働時間の算出が `entry.ts` を見ていて**常に空だった**のを、`at` から出すよう修正。
  - 同名端末は1人にまとめる（保存する参加者は `name` だけを持つため、deviceId 分けは表示に出ない）。
- **残る論点（PM判断）**:
  - **変更履歴（操作ログ）の200件上限はそのまま**。DO のストレージは1キー128KiB上限で、
    日本語込み1件≒200バイト＝**500件で約100KBとほぼ限界**。無制限にすると
    ある時点で DO 書き込みが失敗し同期が壊れるので、上げるならチャンク分割が要る。
    参加者別を切り離した今、上限が効くのは「訂正の経緯を何件さかのぼれるか」だけ。
  - **進行中セッションの変更履歴はルームがある場合のみ他端末と共有**（DO 経由）。
    ルーム無しのソロは端末内のみ。完了後は D1 `store_history` に入るので他端末から見られる。
    ソロでも共有したい場合は D1 テーブル追加＋本番マイグレーションが必要。
- **PM判断**: ⬜未トリアージ

## 2026-08-25: 変更履歴が退室・再読込で消える不具合（提案元: User報告 / Claude Code）

- **報告**: ルームを作らず一人で「品目入力 → 退室 → 別の品目を入力 → 棚卸完了」としたところ、
  **再入室後に入れた分しか変更履歴に残っていなかった**。ルーム作成時も同様の可能性あり。
- **原因**: `auditLog` は `useSync` のメモリ上の配列にしか無く、どこにも永続化していなかった。
  - 下書き（`inv_draft_<id>`）は `{ inv, activeMs }` だけを保存していた
  - 再開（`onSessionResume`）は `clearAuditLog()` を呼ぶが、下書きから戻すものが無い
  - 再読込は `_restoreDraft` を通らない（在庫は `useInventory` 側の保存から戻る）ため、
    そもそも戻す経路が無かった
  - ルームの `init` 受信は `auditLog.splice(0, len, ...msg.auditLog)` の**置き換え**だったので、
    ルームへ入る前にソロで記録した分（`local-` id）も消えていた
  - 結果、完了時の `buildSnapshot(... auditLog ...)` に落ちた分が入らず、履歴の変更履歴が欠けた
- **修正**（実装済み）:
  - 下書きに `audit` を保存し、再開・起動の両方で復元する（`_restoreDraft` / `_restoreDraftAudit`）
  - `useSync.mergeAuditLog()` を追加。id で重複を除き、時刻順に並べ直して上限で切る。
    ルームの `init` 取り込みも置き換えからこれに変更したので、
    **途中でルームを作っても、それまでのソロの履歴が残る**
- **残る限界**:
  - 端末をまたいだ履歴は依然としてルーム（DO）経由でしか共有されない。
    ソロで記録した分は、その端末の下書きが消えると失われる
  - **既に完了した過去のセッションの欠けた履歴は復旧できない**（記録自体が残っていない）
  - 上限200件は据え置き。大規模棚卸で超えると古い分から落ちる
- **PM判断**: ⬜未トリアージ

## 2026-08-24: 品目取込で別名（エイリアス）を取り込まないようにする（提案元: User報告 / Claude Code）

- **報告**: 実データの取込で「エイリアスが1093件ぶつかっています」が出て、全件が衝突扱いになり
  取込が事実上できない。挙がっている別名も品目と無関係（例: `コーヒー豆` の別名が
  `アイスコーヒー粉22`）。
- **原因**: `parseItemCSV` は列を**位置**で決めているのに、5列目が「エイリアス」かどうかを
  **列名で確かめていなかった**。推奨フォーマットの判定は `headers[2] === '単価'` と
  `headers[3] === 'カテゴリ'` だけで、その先の 5列目以降は無検査で
  `aliases / code / categoryCode / prevMonth / lotSize` に割り当てていた。
  5列目が別の意味を持つファイル（規格・旧品名など）では、その列の値が全行の別名として読まれ、
  1つの値を多数の品目が取り合う＝全件衝突になる。
- **対応（今回）**: **別名の取込を止めた**。`parseItemCSV` は5列目を読まず、`row.aliases` は
  常に空になる。結果として衝突は発生せず、別名の解決を選ぶ画面も出ない。
  - **既存の別名（`config.dictionary`）は消さない**。音声入力の名寄せに使うため、
    「ファイルから増やさない」だけにした。
  - 全入れ替えで品目ごと消える場合は、従来どおりその品目の別名も辞書から落ちる。
  - `_planAliases` と衝突解決の規則、確認画面の該当UIは**残してある**（衝突が0件なので出ない）。
    別名の取込を復活させるときに再利用できる。
  - `exportConfigCSV` はエイリアス列を出したまま。列位置を変えると他の取込に影響するため。
- **設計判断（トリアージ希望）**:
  1. **列名を確かめる方向の修正はしていない**。5列目以降を列名で特定する（発注点・軸列と同じ
     やり方）のが本筋だが、今回はユーザー判断で「別名は一旦なし」とした。
     別名を戻すなら、**列名照合とセットで**戻すべき。
  2. 納品取込（`DeliveryImportModal` → `registerAlias`）の名寄せは**触っていない**。
     あちらは行ごとに人が対応づけを選ぶ経路で、今回の一括読み取りとは性質が違う。
- **影響範囲 / 実装状況**: **実装済み**（v0.74.0）。
  - 変更: `app/src/utils/itemImport.js`、および別名取込を前提にしていたtest 5ファイル
  - Worker / D1 / 同期スキーマは無変更。
  - 検証: App 111 files / 1248 tests passed、build 成功。
- **PM判断**: ⬜未トリアージ

## 2026-08-23: 消費推定の記録漏れ検出と、発注点の一括設定（D1・D4）（提案元: Claude Code / 分析）

- **概要**: Dブロックのうち、優先度の高い2件を実装した。
  D1（未記録入庫による過小評価を塞ぐ）と D4（発注点の初期値提案・一括設定）。
  D5（暦要因）・D6（推定の検証）・D8（天気）・D7（月・季節）は未着手。

### D1 — 発注があったはずなのに入庫が無い区間を学習から外す

- **問題**: `impliedConsumption` はマイナス消費だけを `flagged` で除外していた。
  在庫が減ってさえいれば過小評価がそのまま通る（前回10・未記録入庫20・今回5 → 消費5と誤認）。
  過小評価は適正在庫を低くし、**欠品につながる**。部分利用（週1回だけアプリを使う）の店では
  使わない曜日の発注・納品が記録されないため、これが常態化する。
- **対策**: 区間の入庫が0件で、かつ次のどちらかに当てはまれば `missing_inflow` として除外する。
  1. その区間に**発注レコードがある**（スケジュール未設定の店でも効く）
  2. その区間が**発注スケジュールの曜日をまたぐ**（アプリ外で発注していても効く）
- **設計判断**:
  - **区間の両端は含めない**。開始日の発注は前の区間のもの、終端日の発注は納品が次の区間に来る。
    含めると「発注時の在庫入力」がそのまま誤検出になる（既存testが検出した）。
  - `flagged` は真偽のまま、理由を `flagReason`（`negative` / `missing_inflow`）で分けた。
  - `analysisCapability` を拡張し、**観測点が足りていても区間が全滅なら理由つきで「出さない」**。
    記録漏れなら「届いた分を入庫として記録すると算出できます」と次の操作を案内する。
  - 追加入力を求めない。既存データ（発注レコード・発注スケジュール）だけで判定する。

### D4 — 発注点の初期値提案と一括設定

- **背景**: 部分利用のユーザーは曜日別の学習も消費推定も貯まらない。そのあいだ推奨発注数を
  支えるのは手動の発注点なので、**入力の手間を下げることが分析の高度化より先に効く**（D-024）。
- **提案値**（`services/reorderSuggestion.js`）:
  1. `consumption` … 推定日消費 × 発注間隔（本来の定義。次の発注日まで持たせる量）
  2. `stocktakeMin` … 在庫観測の最小値。「これまでで最も少なかったときの在庫」＝実際に
     そこまで減らして回っていた水準。消費が出せない店でも、記録された事実から出せる
  3. どちらも出せなければ **null**（推測で埋めない。理由を画面に出す）
- **一括設定画面**（`ReorderBulkModal`）: 未設定のみ表示、目安の個別採用、
  「提案をまとめて採用」（**未設定かつ目安がある品目だけ**を埋め、設定済みは上書きしない）。
  在庫タブのフィルター行から開く。
- 既存の「目安を採用」（詳細シート）も同じサービスへ寄せ、二重実装にしていない。

- **影響範囲 / 実装状況**: **実装済み**（`claude/develop-branch-review-1gyvy2` / v0.72.0）。
  - 新規: `services/reorderSuggestion.js`、`components/ReorderBulkModal.vue`（＋各test）
  - 変更: `services/impliedConsumption.js`、`services/analysisCapability.js`、
    `MovementPage.vue`、`App.vue`
  - D1 の除外は**既存の推奨・目安すべてに効く**（`avgDailyConsumption` 経由）。
    これまで出ていた数字が「出なくなる」ケースがあるが、それは誤った数字を止めた結果。
  - D1 / Worker / D1スキーマは無変更。
  - 検証: App 110 files / 1247 tests passed、build 成功。実機確認は未実施。
- **残件**: D6（推定の検証：推定 vs 実際）→ D5（暦要因を推奨に効かせる）→ D8（天気）。
  D7（月・季節）はサンプル数が足りないため1年後。

## 2026-08-23: 発注数の決め方と「補充目標」を実装（C完了）（提案元: Claude Code / UI）

- **概要**: 発注数の決め方に **モードA（自分で入力）/ モードB（不足分を自動）** を用意し、
  不足を測る相手として **補充目標**（発注してここまで戻す水準）を導入した。

## 2026-07-28: アカウント登録の拡張（復旧用メール・PIN復旧・登録時アンケート）（提案元: Claude Code / User構想の設計整理）

- **概要**: 店舗アカウントへ**任意の復旧用メールアドレス**を追加してPIN紛失時の自己復旧を可能にし、
  登録時に業種・使用目的の簡易アンケートを取る。**実装時期は未定**で、本エントリは設計の先行確定のみ。
- **背景・根拠**:
  - 現在の識別子は `shop_code + 4桁PIN` だけで、**PINを失うと店舗データへの復旧手段が一切ない**
    （`handleLogin` はPIN照合のみ、`stores.pin_hash` を再設定する経路が存在しない）。
    公開後にサポート負荷として跳ね返る性質の欠落であり、動機は正当。
  - アンケートは業種別の初期辞書・品目テンプレの精度、および機能／料金の優先順位判断に効く。

### 設計判断（PMトリアージ希望）

**1. メールを identity にせず「復旧用の連絡先」に留める（最重要）**

`enterprise-design.md` §9.1 は「店舗＝共有アカウント（`shop_code + PIN` を知る全員が同一識別）」を
*業種特性に合った良い割り切り*として明示採用し、§9.2 でメール認証は **org_admins（本部層）** に置いている
（`org_admins` は `email` を主キーに持つ）。店舗レイヤーの identity をメールへ移すと、この2階層設計と衝突する。
飲食店の現場は複数スタッフが同一店舗コードで入る運用のため、メール＝ログインIDにすると運用も壊れる。

→ `stores` へ復旧用メール（任意・確認済みフラグ付き）を足すだけに留め、**ログインは従来どおり
`shop_code + PIN`** とする。これなら enterprise 設計と矛盾せず、将来 org 層を載せる余地も残る。

**2. PIN復旧は「ログイン相当」であり、単一ホストセッションの副作用を伴う**

`authHandler.js:142` はログイン成功時に `DELETE FROM auth_tokens WHERE shop_code = ?` で他端末を全失効させる。
復旧を同じ扱いにすると**棚卸作業中の他端末が落ちる**。乗っ取り対策としては全失効が正しいので、
挙動は維持したうえでUIに「他の端末はログアウトされます」を明示する。

**3. 4桁PINとメール復旧の強度差を埋める条件**

PINは10,000通りで、現在は15分5回のレート制限（`shop_code` 単位）が実質的な防御。メール到達だけでPINを
再設定できるようにすると、**アカウントの実強度＝メールアカウントの強度**になる。一般的な設計だが、
以下を満たさないと `SEC-001`〜`SEC-004` で閉じた認可境界を迂回される。

- 復旧トークンは**単回使用・短命（15〜30分）・ハッシュ化して保存**
- 復旧完了時に **auth_tokens とホストトークンを全失効**
- 復旧要求のレート制限（メール単位＋IP単位。既存 `ip_attempts` を流用可）
- **列挙対策**: 復旧要求の応答は、メールの登録有無にかかわらず常に同一にする。
  メールから店舗コードを引ける導線を作ると、`shop_code` を知らない攻撃者が対象を特定できるようになる
- **未確認メールでは復旧不可**（確認済みフラグ必須）。登録直後の確認メールで確定させる

復旧方式は User 未決。比較は下表（`SEC-006` の脅威モデルと合わせて確定させたい）。

| 方式 | 利点 | 弱点 | 備考 |
|---|---|---|---|
| メールに復旧リンク | 実装が単純。桁数の総当たりが無い | メールクライアントのプリフェッチで単回トークンが消費され得る | 消費はGET不使用（確認画面＋POST）で回避 |
| メールに数字コード | スマホでアプリ内完結。端末を移らない | コード総当たりの余地。試行回数制限が必須 | 6桁＋5回上限＋短命なら実用強度 |
| 併用 | 双方の導線を吸収 | 実装・テスト量が2倍 | 初版では非推奨 |

**4. 削除範囲の変更（`PLAY-001` の承認済み data map に影響）**

`accountDeletion.js` は現在13グループを物理削除し `stores` を匿名 tombstone 化する。メール・復旧トークン・
アンケート回答を**追加列挙**し、`0011` と同型の active-insert トリガを新テーブルにも付ける必要がある。

新論点: **7日 tombstone の間に同じメールで再登録できるか**。tombstone に生メールを残すと「削除したのに
保持されている」ことになり、消すと再登録時の重複検知ができない。→ **ハッシュのみ7日保持**を推奨する。

**5. アンケートは任意・目的限定**

業種・使用目的も Data Safety の申告対象。必須にすると登録離脱を招き、Play の「機能に不要なデータ収集」
観点でも不利。→ **スキップ可**とし、目的（初期テンプレの出し分け・改善統計）を画面に明示、
個人特定に使わない旨を privacy へ記載する。

**6. メール配信基盤の選定が前提作業**

現在バックエンドに送信経路が一切ない（`worker/src` に該当実装なし）。構成上は Cloudflare Email Service

先行タスクになるため、canonical host（`DS-08`）の決定と同じタイミングで決めるのが効率的。

- **影響範囲 / 実装状況**: **実装なし（設計提案のみ）**。実装する場合に触る範囲:
  - migration 新規（`stores.recovery_email` / `recovery_email_verified_at` / 復旧トークン表 / アンケート回答表）

## 2026-07-17: 発注点は「人間が決める床＋データの推奨」の二段構え（提案元: カード/入出庫セッション）

- **概要**: 手動発注点＝人間が決める絶対下限（床）として扱う。予測モデルは発注点/発注量の
  「推奨」を出す側で、**手動値は自動上書きしない**（タップ採用で合成。実務は `max(手動床, 推奨)` が安全側）。
- **背景・根拠**: 在庫理論では別レイヤー。
  - **発注点(ROP)**＝*いつ*頼むか＝リードタイム中の予測需要＋安全在庫
  - **発注量**＝*いくつ*頼むか＝次納品までの予測需要＋安全在庫−現在庫（曜日別・外的/内的要因はここ）
  - **安全在庫**＝*切らせない*緩衝＝需要のブレ×リードタイム×目標欠品率
  - 「これさえ守れば絶対切れない」は数学的に不可能。実装上は**サービスレベル（欠品率）で安全在庫の大きさを選ぶ**話に落ちる。
  - 発注点はリードタイム前提で意味を持つ → 他セッションの**発注スケジュール（発注曜日/締切）がリードタイム構造**、
    **需要カレンダー（祝日・給料日等）が外的要因**として噛み合う。
- **料金戦略との整合**: 手動発注点＝シンプル/データ不要＝**無料の床でも出せる**。
  予測（曜日別・外的/内的要因）の推奨＝データと計算＝**有料の差別化**。`pricing-strategy.md` の wedge と一致。
- **影響範囲 / 実装状況**: 実装済み（`5e918d6` ほか）。
  - `reorderPoints` を config フィールド化（default/serialize/assign/rename/remove/setter＋RoomDO中継。localStorage/D1/ルーム同期）
  - 「要補充」判定を `理論在庫 ≤ 発注点`（未設定は0以下）に。在庫タブのフィルタ・件数・強調が連動
  - 在庫タブの品目詳細に手動入力＋**暫定「目安」**（直近30日の平均日消費 × 発注間隔）。タップ採用・自動上書きなし
  - 暫定ヒューリスティックは需要カレンダー/曜日別モデル完成時に置換予定
- **PM判断**: ✅採用（2026-07-18 PMセッション）
  - 反映先: `ordering-analytics-design.md` §2.3（パー→発注点の二段構えとして全面更新・用語定義も同節に収録）、
    同書ヘッダの実装状況、`roadmap.md` E節。
  - 採用理由: ①在庫理論と整合（ROP/発注量/安全在庫のレイヤー分離）②「手動値を自動上書きしない」は
    本プロダクトの原則「勘を潰さず、目安を出す」と一致 ③無料の床=手動/有料=予測の切り分けが
    `pricing-strategy.md` の wedge と噛み合う。
  - 補足条件: 「絶対切らさない」は数学的に不可能のため、UI文言では「切れにくくする目安」等の
    表現を使い、保証と誤読される語（必ず・絶対）を避けること（レビュー時に確認する）。

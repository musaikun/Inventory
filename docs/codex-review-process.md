# Codex横断レビュー運用プロセス

最終更新: 2026-07-21 / 位置づけ: Claude Code 6セッション体制を崩さず、CodexをPM/QA/セキュリティ/DB設計/docs整合性の横断レビュー担当として使うための運用定義。

---

## 1. 目的

このプロジェクトでは、機能開発の主担当は引き続き Claude Code 側の6セッションとする。
Codex は「7つ目の機能実装セッション」ではなく、節目ごとに全体を見直して **全部A評価へ近づけるための品質ゲート** として使う。

Codex の主目的は次の4つ。

1. docs と実装のズレを早期発見する
2. PM/QA/セキュリティ/DB設計/運用の横断リスクを P0〜P3 に整理する
3. Claude Code に渡しやすい作業チケットへ分解する
4. Claude Code 側の対応完了後に再レビューし、次の指摘スタックを更新する

---

## 2. 基本分担

| 領域 | 主担当 | 補足 |
|---|---|---|
| 新機能の本実装 | Claude Code | 既存6セッションの文脈・担当領域を維持する |
| UI/UXの大きな変更 | Claude Code | Codexはレビュー・受け入れ条件・リスク指摘に回る |
| バグ修正 | Claude Code | ただし小さな品質修正はCodexでも可 |
| PMレビュー | Codex | 現状確認、優先順位、指摘スタック化 |
| QAレビュー | Codex | テスト不足、回帰リスク、リリース判定 |
| セキュリティレビュー | Codex | P0/P1の小改修はCodex実装可 |
| DB設計レビュー | Codex | 設計案・矛盾検出・テスト観点作成が主 |
| docs整合性 | Codex | 実装とdocsのズレ、古い記述、反映漏れを確認 |
| リリース前GO/NO-GO | Codex | テスト・ビルド・P0有無・docs更新を確認 |

---

## 3. Codexがやること

### 3.1 定期横断レビュー

節目ごとに次を確認する。

- `docs/project-status.md` と実装の一致
- `docs/roadmap.md` の優先順位と実態の一致
- `docs/security-review.md` の未解決項目
- `docs/intake-reviews.md` / `docs/proposals.md` の反映漏れ
- DB migration と Worker API / クライアント実装の整合性
- localStorage / D1 / Durable Objects / R2 の責務分担
- app / worker のテスト結果
- app build 結果
- P0/P1ブロッカーの有無

### 3.2 指摘スタック化

レビュー結果は必ず P0〜P3 で分類する。
単なる感想ではなく、Claude Code がそのまま動ける粒度にする。

### 3.3 Claude Code向けチケット化

各チケットには最低限、次を含める。

- 目的
- 背景 / なぜ必要か
- 対象ファイル候補
- 実装方針
- 受け入れ条件
- テスト観点
- docs更新要否
- 優先度
- Codexで再レビューすべき観点

### 3.4 再レビュー

Claude Code 側で対応が完了したら、Codex は次を行う。

1. 差分確認
2. テスト / ビルド実行
3. docs更新確認
4. 指摘スタックの解決判定
5. 新たに発覚したリスクの追加
6. 次の優先チケット提示

---

## 4. 優先度定義

### P0: 即対応 / リリースブロッカー

放置すると、データ損失、セキュリティ事故、法務違反、重大な信用毀損、またはリリース不能につながるもの。

例:

- 重要データが localStorage のみで端末故障時に消える
- ゲスト権限で原価・価格など秘匿情報が見える
- 認証なしで店舗データやPDF処理にアクセスできる
- CORS / CSP / レート制限が本番運用に耐えない
- アカウント削除手段がない
- 位置情報や外部送信がプライバシーポリシーに未反映
- バックアップとリストア手順がない
- 本番ビルドや主要テストが落ちる

### P1: 商用化・継続利用に強く効くもの

即リリース停止ではないが、有料化、継続利用、企業商談、Google Play公開、サポート品質に大きく影響するもの。

例:

- 監視・アラートがない
- 障害調査に必要なログやrunbookがない
- PIN忘れ時の復旧手段がない
- 課金プラン境界がサーバーとクライアントで不一致
- 上層部向けレポートや生産性分析が不足している
- READMEや運用手順が不足し、引き継ぎ困難

### P2: 次の大機能前に片付けたい設計・品質問題

今すぐ事故にはならないが、放置すると開発速度、変更容易性、回帰リスクに悪影響が出るもの。

例:

- `App.vue` の肥大化
- `useSync.js` の責務過多
- config serialize と worker normalizeConfig の突き合わせ不足
- 同期・再接続・オフラインのE2E不足
- APIレスポンス仕様が暗黙
- migration と実装の責務不一致

### P3: 改善・整理・将来対応

今やらなくてもよいが、時間があるときに進めると長期的に効くもの。

例:

- README整備
- docsの見出し整理
- 将来のAI発注メモ
- 将来の企業向けSSO検討
- 連携APIの設計メモ
- UI文言の細部改善

---

## 5. Codexがコード修正してよい条件

Codexは原則レビュー担当だが、次の条件をすべて満たす場合は小修正を行ってよい。

1. 新機能ではない
2. 既存仕様を守るための修正である
3. 影響範囲が限定的
4. テストを書ける、または既存テストで守れる
5. docsと整合する
6. Claude Codeの進行中タスクと衝突しない
7. P0/P1の品質・セキュリティ・データ整合性に関係する

例:

- 小さな回帰テスト追加
- セキュリティヘッダ追加
- PDFガードのテスト追加
- ゲスト向け秘匿データサニタイズ
- config不一致を検出するテスト
- docsの反映漏れ修正
- README/運用docs整備

---

## 6. Codexが勝手に実装しないこと

次の作業は、Codexが案を出すことはできるが、原則として本実装は Claude Code または人間の判断後に行う。

- 新機能の本実装
- 大きなUI/UX変更
- 破壊的DB migration
- 既存ユーザーデータに影響する変更
- 課金・契約・権限モデルの変更
- 多店舗/組織モデルの本実装
- アカウント削除ポリシーなど法務判断が必要な変更
- Claude Codeの担当セッションと衝突する変更

## 7. 推奨ワークフロー

### 7.1 通常サイクル

```text
Claude Code各セッションが機能・修正を実装
  ↓
Codexが横断レビュー
  ↓

  ↓

  ↓
Claude Codeが対応
  ↓
Codexが再レビュー
  ↓
問題なければ次のチケットへ進む
```

### 7.2 リリース前サイクル

```text
リリース候補ブランチ作成
  ↓

  ↓
GO / NO-GO 判定
  ↓
NO-GOならClaude Codeへ修正チケット化
  ↓
修正後にCodexが再レビュー
```

## 8. ブランチ集約ルール

現在、Claude Code の全セッションは `claude/restaurant-inventory-system-0XNHA` に集約している。
Codex も同じ前提に揃える。

### 8.1 原則

- Codex のレビュー結果・docs修正・小さな品質修正も `claude/restaurant-inventory-system-0XNHA` に集約する。
- Codex は、作業開始時に対象ブランチ・未コミット差分・直近コミットを確認する。
- push 前に app / worker の必要テストと、docs差分の整合性を確認する。
- remote が無い、または対象ブランチへ push できない環境では、ローカルコミットとPRメタデータ作成まで行い、push不可理由を明示する。

### 8.2 このルールの懸念

全セッションを1ブランチに集約する運用は、文脈を一本化できる反面、次の懸念がある。

1. **競合が増えやすい** — 特に `docs/project-status.md`、`docs/roadmap.md`、`docs/proposals.md`、`App.vue` は複数セッションが触りやすい。
2. **未完成作業が混ざりやすい** — 1ブランチに全作業が入るため、リリース可能状態と作業途中状態の境目が曖昧になる。
3. **レビュー単位が大きくなりやすい** — 小さなPR単位ではなく、複数セッション分の差分をまとめて見る必要が出る。
4. **docsの衝突が起きやすい** — PM判断や提案の追記が同じファイルに集中する。

ただし、現時点ではメリットも大きい。

- 全セッションの前提が揃いやすい
- PMレビューで現在地を把握しやすい
- 小規模チームではブランチ管理コストを抑えられる
- 仕様が固まり切っていない段階では、統合先を一本化した方が判断が速い

したがって、当面は `claude/restaurant-inventory-system-0XNHA` 集約でよい。
ただし、Codex はレビュー時に **未完成差分の混入・docs衝突・P0未解決のままの積み上げ** を必ず確認する。

### 8.3 将来分岐する条件

次のいずれかが起きたら、作業ブランチ分割を検討する。

- 同じファイルの競合が頻発する
- リリース候補を安定化できない
- P0修正と大機能開発が混ざってレビュー不能になる
- 複数セッションが同じ領域を同時に大きく変更する
- PR差分が大きすぎて人間レビューが困難になる

## 9. `docs/proposals.md` の要約トリアージ運用

`docs/proposals.md` は、PMセッション以外の実装/戦略セッションが PM判断に関する提案を `⬜未トリアージ` で集約する場所である。
内容が長くなった場合、Codex は全文をそのまま処理するのではなく、まず **要約テーブル + 箇条書き確認** に落とす。

### 9.1 Codexが確認すること

- 未トリアージ項目の一覧
- すでに実装済みだがPM判断だけ残っている項目
- 採用済みだが恒久docsへの反映先が未記入の項目
- `roadmap.md` / `project-status.md` / `security-review.md` へ反映済みか
- 同じ論点が重複していないか
- P0/P1に昇格すべき提案が埋もれていないか

### 9.2 要約フォーマット

Codex はレビュー時に、まず次の形式で短く整理する。

```md
## proposals.md 要約トリアージ

### 未トリアージ
- [P0/P1/P2/P3] タイトル — 何を判断すべきか / 推奨判断 / 反映先候補

### 採用済み・反映確認が必要
- タイトル — 反映済みdocs / 未反映docs / 次アクション

### 保留・却下候補
- タイトル — 保留理由 / 再判断条件

### 重複・統合候補
- A と B は同じ論点。恒久docsでは1項目に統合する。
```

### 9.3 運用方針

- `docs/proposals.md` は削除前提の作業メモではなく、判断履歴として残す。
- ただし、長文化した場合は Codex が要約を作り、PMが確認しやすい粒度にする。
- 採用済み項目は、恒久docsへの反映先を明記したうえで記録として残す。
- 本文を大きく削る場合は、先に要約案を提示し、人間またはPMセッションの確認後に行う。
- Codex が勝手にPM判断を確定しない。Codexは「推奨判断」と「理由」を出す。

## 10. 最初に着手するべき領域

最初のサイクルでは、新機能ではなく **Wave 2.5: 信頼性と収益化準備** を優先する。

推奨順は次の通り。

1. P0-01: 入出庫のD1同期
2. P0-02: セキュリティ小改修（CORS / CSP / PDFガード / WSゲスト prices サニタイズ）
3. P0-03: 日次バックアップ cron → R2 とリストア手順
4. P0-04: 退会・アカウント削除フロー
5. P1-01: 最小監視と認証テーブル掃除 cron
6. P2-01: config serialize ⇔ worker normalizeConfig 突き合わせテスト
7. P2-02: 同期E2Eスモークテスト

この順番にする理由は、商用化・Play公開・企業商談のいずれに進む場合でも、データ耐久性、セキュリティ、削除導線、監視が前提になるため。

## 11. チケットテンプレート

```md
## Ticket: <ID> <タイトル>

### 優先度
P0 / P1 / P2 / P3

### 目的
何を達成するか。

### 背景
なぜ今必要か。どのリスクを潰すか。

### 対象ファイル候補
- `path/to/file`

### 実装方針
大まかな方針。詳細設計が必要な場合はここで明示する。

### 受け入れ条件
- 条件1
- 条件2
- 条件3

### テスト観点
- 単体テスト
- Worker/APIテスト
- 手動確認
- 必要ならE2E

### docs更新
必要 / 不要。必要な場合は対象docsを書く。

### Codex再レビュー観点
対応後にCodexが重点的に見るポイント。
```

## 12. 最初のレビュー依頼テンプレート

```text
Codex横断レビューをしてください。

目的:
- PM/QA/セキュリティ/DB設計/docs整合性の観点で、A評価に足りないギャップを洗い出す
- P0〜P3に分類する
- Claude Codeの6セッションに渡せる作業チケットにする

制約:
- 新機能実装はしない
- ただし、小さなテスト追加、セキュリティ修正、データ整合性修正、docs修正は提案してよい
- 実装する場合は、Codexで修正してよい範囲とClaude Codeに渡すべき範囲を分ける

出力:
1. 現状評価
2. P0〜P3指摘スタック
3. Claude Code向けチケット
4. Codexで対応可能な小修正
5. リリース可否
6. 次回レビュー観点
```

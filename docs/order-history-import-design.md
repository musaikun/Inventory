# 過去発注（納品）履歴 取込 設計（たたき台 v1）

棚卸アプリに「**過去の納品履歴を取り込み、そこから発注の理論値を逆算する**」機能を載せるための設計図。
本書は羅針盤（`docs/strategy-10yr.md`）・発注アシスト設計（`docs/ordering-analytics-design.md`）配下の実装計画。実装前に本書で合意を取る。

関連：`docs/db-design-v2.md`（`deliveries` / `item_par_levels` テーブル）、`app/src/composables/useOrders.js`（発注レコードの器）、`app/src/composables/usePdfImporter.js`（現行の取込）。

---

## 0. 設計思想（最重要）

- **入力はその瞬間に価値を返すものだけが現場で続く。** 過去履歴の取込は「データ収集」ではなく、**予測のコールドスタート解消**と**品目マスタの自動生成**という即時価値を返す一手。
- **全自動・任意フォーマットは狙わない。** 業界の勝ち筋は「AI-OCR/テンプレ学習 ＋ 人手レビュー」。本設計も **レシピ（テンプレ）学習＋確認レビューで“実質全部”を捌く**方針。
- **仕入情報を外に出さない。** 現行のPDF/Excel解析は端末内完結（外部送信なし）。この原則を既定として維持する。LLM抽出はこの原則に抵触するため opt-in の上級機能に隔離する（§7）。
- **甘い数字を出さない。** 逆算した発注理論値には常に信頼度を添える（`app/src/utils/analysisQuality.js` の思想）。データが薄い間は「参考」表示に留める。

## 1. なぜやるか（価値）

| 価値 | 内容 |
|---|---|
| **予測のコールドスタート解消** | `orderLearning.parLevel` はサンプル0で `null`。過去履歴を入れれば**初日から**「前回発注量・曜日別」が出る。`ordering-analytics-design.md` §4ラダーの「数週間ためないと立ち上がらない」問題を過去データで即埋める。 |
| **品目マスタの自動生成** | 履歴には品目名・単価・単位・入数・仕入先が全部入っている。棚卸の品目リスト作成（今はCSV手作業）を履歴から自動生成でき、**未セットアップ店の立ち上げが一撃**。 |
| **仕入先軸の自動構築** | supplier 別グルーピングが履歴から埋まる（汎用2軸の「仕入先」）。 |
| **フロー分析の遡及** | `deliveries` 相当。消費量・原価推移の過去分を後付けで得られる。 |

## 2. 前提とデータの割り切り

- **過去データは納品（deliveries）として扱う。** 現場が持っているのは納品書・請求書＝「届いた量」。発注（頼んだ量）ではない。
- **発注時在庫（stock）は無い。** 過去履歴に在庫は付いていない。→ `stock:null, postStock:null` で投入する。既存 `getLearningEvents` は postStock=null を除外するので、**現在の postStock 学習を一切壊さない**。
- **過去データの使い道**：①発注理論値の逆算（§4）②品目マスタ生成（§5）。postStock ベースの厳密学習には使わない。
- **発注 ≈ 納品と当面割り切る。** 概念上は別（`orders`＝発注／`deliveries`＝納品）だが、まずは納品を主データとして扱い、`source:'import'` 印で手入力と区別する。将来フロー分析を厳密化する段で D1 `deliveries` に正式分離。

### 2.1 レコード形（既存 useOrders に最小追加）

```js
{ id, date, supplier, axis:'仕入先', sessionId:null,
  type:  'delivery',          // 追加: order / delivery の区別
  source:'import',            // 追加: 手入力と区別（まとめ取消・再取込用）
  importBatchId:'imp_xxx',    // 追加: 取込単位（冪等な再取込・一括取消用）
  lines:[{ item, qty, unit, unitPrice, stock:null, lot, postStock:null }] }
```

## 3. 取込アーキテクチャ ― 中間フォーマットに集約する

バラバラなフォーマット問題は、**1本の中間フォーマット（canonical）を決め、全ての入口をそこへ変換する**ことで解く。取込ロジック（投入・重複排除・日付展開）は中間フォーマットだけを相手にし、入口の増設（新業者・新レシピ）を疎結合にする。

```
[業者PDF] ─レシピA─┐
[業者Excel]─レシピB─┤
[自己CSV] ─列マッピング┤→ ★中間フォーマットCSV → [名寄せ] → [ステージング/確認] → [確定投入]
[写真]    ─OCR(後段)─┤     (date,supplier,category,
[LLM抽出] ─opt-in───┘      item,qty,unit,price,...)
```

### 3.1 中間フォーマット（一括インポートCSV）

アプリ純正の取込CSV。テンプレDL可能にする。**各行に日付があるので1ファイルで複数日を一括投入**（行の日付ごとに納品レコードへ展開）。

```
日付, 仕入先, カテゴリ, 品目名, 数量, 単位, 単価, 商品コード, 入数
2026-06-01, 八百屋青果, 野菜, 玉ねぎ, 2, ケース, 3800, , 10
2026-06-01, 肉のヤマ,   肉,   鶏もも, 5, kg,     980,  , 1
2026-06-03, 八百屋青果, 野菜, レタス, 3, ケース, 2400, , 8
```

- 中堅企業のシステム担当は、自社エクスポートを**この1形式に1回マッピングするだけ**で以後流し込める（レシピ不要の最短ルート）。
- 列は必須（日付・品目名・数量）と任意（仕入先・カテゴリ・単位・単価・商品コード・入数）に分ける。

### 3.2 レシピ（フォーマット別プロファイル）

「あるフォーマットを中間形式に変換する保存済みプロファイル」。現行の単一PDFパーサ／Excel列固定は「レシピ1号・2号」として畳み込む。

```js
Recipe {
  id, name,                    // 例: 'トーホー納品書PDF'
  fileType: 'pdf'|'excel'|'csv',
  signature: { keywords:[...], pageSizeHint, headerCells:[...] },  // 自動判定用の指紋
  extract: { ... },            // 列index or 座標アンカーの抽出ルール
  categoryLocus, dateLocus,    // カテゴリ・日付の在り処
}
```

- **自動判定＋手動選択の二段**：署名でファイルを指紋照合し、当たれば自動適用。曖昧なら候補提示→ユーザー選択。選んだら学習して次回自動。
- 保存先：localStorage（当面）→ D1（共有・端末間同期は後段）。
- **レシピ共有＝事業の堀**：主要業務用卸（トーホー・久世・西原商会等）は多店舗で共通。1度書いたレシピを配布・蓄積する仕組みはネットワーク効果になる（将来構想・§9）。

### 3.3 複数ファイル一括アップロード

現状 `parsePdfFile` は1ファイル。複数受け取り→各ファイルにレシピ自動判定→**結果を連結して1データセットに統合**へ拡張。
- **ジャンル別にPDFが分かれる現実にドンピシャ**（各PDFが内部にカテゴリを持つ＝`findCategory`）。12枚を放り込む→1つの納品データに統合。
- **取込済みファイルの記録**を持ち、後日追加分だけ足す運用（一括でない現実）に対応。

## 4. 発注理論値の逆算 ― 2段構成

過去は「納品」として持ち、そこから**発注の理論値**を逆算する。`消費 = 前回在庫 + 納品 − 今回在庫` の設計思想に乗る。

### 4.1 段①：納品実績ベース（今すぐ・確実）

納品履歴＝その店が実際にどう仕入れていたかそのもの。「逆算」というより「再現」で信頼度が高い。
- **前回納品量** → 次回発注の目安（既存 `getLastOrderQty` がそのまま使える）
- **曜日別／週別の平均納品量**（外れ値に強い `medianEstimator` を流用）
- 納品データ**だけ**で出る。数ヶ月あれば季節性の当たりも付く。

### 4.2 段②：消費逆算ベース（賢い・より正しい発注点）

納品は塊で届くので、納品の曜日 ≠ 消費の曜日。**消費速度に一度ならす**：

```
長期平均では  総納品量 ≈ 総消費量        （期首在庫 ≈ 期末在庫 で相殺）
平均日次消費 = 期間内の総納品量 ÷ 日数
発注理論点(reorder_point) = 平均日次消費 × リードタイム日数 + 安全在庫
発注理論量(reorder_qty)   = 平均日次消費 × カバー日数 − 現在庫 + 安全在庫  → ÷入数 切り上げ
```

`ordering-analytics-design.md` の `parEmpirical`（平均使用×リードタイム＋安全在庫）と、`db-design-v2.md` §4.5b `item_par_levels`（reorder_point / reorder_qty / lead_days）を**過去納品を入れた瞬間に埋める**のが取込の最大価値。

### 4.3 逆算で外せない4つの肝

1. **入数(lot)変換** — 消費は物理量(kg/本)、発注は入数単位(ケース)。「理論消費 ÷ lot → 切り上げ → 理論ケース数」。既存 `services/lot.js`（`effectiveLot`）と `postOrderStock` が lot を掛ける実装をそのまま使う。
2. **外れ値除外** — 仕込み・イベントの臨時大量納品が理論値を歪める。`medianEstimator`（中央値）＋既存 `excluded` フラグで守る。
3. **リードタイム・安全在庫** — 品目/仕入先ごと。手動 or 「発注間隔の実測」から推定。§4.4 の納品カレンダーで扱う。
4. **信頼度を必ず添える** — 納品**だけ**だと消費の分解能が粗い。**棚卸(在庫スナップショット)が1点でも入ると精度が跳ねる**（`消費 = 期首 + 納品 − 期末` が厳密に解ける）。データが薄い間は理論値を「参考」表示に。

### 4.4 納品カレンダー ― カバー期間が発注日ごとに変わる

発注→納品のリードタイムと**休配日**を織り込むと、理論発注量の「カバー期間」が発注日ごとに変わる。

```js
DeliverySchedule (仕入先別・店デフォルトあり) {
  cutoff:           '11:00',            // 締め時刻
  leadBeforeCutoff: 1,                  // 締め前発注 → 翌日納品
  leadAfterCutoff:  2,                  // 締め後発注 → 翌々日
  deliveryWeekdays: [月,火,木,金,土],    // 日・水は休配
  holidays:         ['2026-08-15', ...] // 臨時休配（お盆・年末）
}
```

**カバー期間ロジック**（各納品は「その納品日〜次の納品日」を賄う）：

```
カバー日数(納品日) = 次の納品日 − その納品日
理論発注量 = 平均日次消費 × カバー日数 − 現在庫 + 安全在庫  → ÷入数 切り上げ
```

例（締め前=翌日納品／日・水休配）：

| 発注日 | 納品日 | 次の納品 | カバー日数 | 発注量 |
|---|---|---|---|---|
| 金 | 土 | 月（日は休配） | **2日** | **多め** |
| 月 | 火 | 木（水は休配） | **2日** | **多め** |
| その他 | 翌日 | その翌日 | 1日 | 通常 |

→「日曜前・水曜前の発注が多くなる」が**カレンダーから自動導出**される（品目ごとの特別処理は不要）。締め時刻超過も同じ計算（リード2日）に乗る。

**同じカレンダーが二重に効く**（過去の消費分解にも使う）：

```
各納品の日次消費 = 納品量 ÷ その納品のカバー日数
```

土曜納品（2日分）を単純に1日消費と見なすと過大評価になる。カレンダーで割って正しく均す。**過去を分解する式と、未来の理論発注を組む式が同じカレンダーで一貫**する。

**計算 vs ユーザー入力（両方）**：
- **自動推定**：納品履歴の日付から**納品曜日・休配日・発注サイクル**を推定（日・水が一度も出てこない＝休配）。取込時に自動プリフィル。
- **ユーザー入力**：**締め時刻・リードタイム・臨時休配**は日付だけからは分からない。設定画面で入力（推定値を初期表示して確認・上書き）。
- **仕入先別**：業者ごとに締め・曜日が違うので `supplier` キーで持ち、無ければ店デフォルト。

**再計算**：理論値は純関数の派生値（`orderLearning` / `orderSuggestion` と同設計）。カレンダー・安全在庫を変えたら**その場で全品目を再計算**。値は保存せず都度算出、もしくは schedule 変更をトリガにキャッシュ更新。

## 5. 品目マスタの自動生成

納品履歴から品目リスト（`config.order` / `units` / `prices` / `categories` / `codes` / `lotSizes` / 仕入先軸）を生成。
- 未セットアップ店が履歴を入れるだけで棚卸の品目リストまで立ち上がる。
- 既存 `loadFromCSVMapped` / `itemsToConfigCSV` の変換を流用。同名統合は既存ロジック（品目名の完全一致で1件）に乗せる。
- 単価は「直近の納品単価」を採用（当時単価は明細に焼き込み済み＝分析用に別途保持）。

## 6. 名寄せ・ステージング・冪等性（信頼性の核）

乱雑データの信頼性はここで決まる。**取込は即確定せず、下書きに溜めて差分を見せる。**

1. **名寄せ（業者名→品目）** — 「北海道産玉ねぎL 10kg」→「玉ねぎ」。辞書3層（`dictionary` / `learnedAliases` / `masterDict`）＋その場対応づけで半自動。対応づけたら `masterDict` に焼き、**業者ごとに永続化**して2回目以降は自動。未マッチは「新規品目追加 / スキップ」。
2. **ステージング＆差分確認** — 確定前に「新規品目◯件／既存マッチ◯件／未マッチ◯件／重複◯件」を提示。ユーザーが直してから確定。
3. **冪等な再取込（重複排除キー）** — `日付+仕入先+品目+数量` のハッシュ、またはファイル指紋で、**同じPDFを2回落としても二重にならない**。`importBatchId` で一括取消・再取込も可能に。

## 7. LLM抽出（opt-in・プライバシー隔離）

「任意フォーマット」の最後の一手。PDF/画像テキスト→構造化をLLMで行う。
- **強力だが、現行の「仕入情報を外に出さない」原則と衝突**。既定オフの上級機能に隔離する。
- 実装時の要件：自前Worker経由・明示同意・単価等のマスキング検討・抽出結果は必ず §6 のステージングで人手確認。
- 位置づけ：レシピが無い長尾フォーマットの救済。主軸はあくまで端末内レシピ＋中間CSV。

## 8. 類似サービス・定石（設計の裏付け）

この領域は「全自動・任意フォーマット」を掲げる所は無く、勝ち筋が定まっている。

| サービス | 学べること |
|---|---|
| **クロスマート** | 飲食店の納品書・請求書のデータ化（OCR＋人手補正）。本要望に最も近い。 |
| **バクラク / invox受取請求書 / TOKIUM / Bill One** | 請求書AI-OCR。共通定石＝**AI-OCR ＋ 仕入先ごとのテンプレ学習 ＋ 人手レビュー**。「レシピを覚える」はこれと同発想。 |
| **タノム / インフォマート** | 受発注のデジタル化（発注の前段。going-forward）。過去取込とは別軸だが連携先候補。 |
| **銀行明細インポート（マネーフォワード / YNAB）** | 「どの銀行もCSVが違う」を**金融機関ごとのインポートプロファイル＋列マッピング記憶**で解決。「業者ごとにフォーマットが違う」と構造が同型。プロファイル選択→マッピング→次回自動のUXが参考。 |

**教訓：全自動を狙わず、テンプレ学習＋確認レビューで“実質全部”を捌く。**

## 9. 段階計画

| 段階 | 内容 | 立ち上がる価値 |
|---|---|---|
| **P0** | 中間フォーマットCSV（日付入り・一括/単日）＋名寄せ＋ステージング/冪等 → 納品レコード投入 | 予測コールドスタート解消の器 |
| **P1** | 品目マスタ自動生成（order/units/prices/仕入先軸） | 未セットアップ店の立ち上げが一撃 |
| **P2** | 段①：納品実績ベースの発注理論値（前回量・曜日別。純関数で即） | 発注アシスト稼働 |
| **P3** | 段②：消費逆算＋納品カレンダー（`item_par_levels` を埋める）＋信頼度 | 休配日込みの理論発注 |
| **P4** | 複数ファイル一括＋PDFレシピ（自動判定/選択） | ジャンル別PDFの現実に対応 |
| **P5** | 棚卸を1点でも組合せて精度ブースト、D1 `deliveries` 永続化＋端末間同期 | 分析基盤・多端末 |
| **保留** | LLM抽出（opt-in）、写真OCR、レシピ共有（堀） | 長尾・将来構想 |

依存：P0→(P1,P2)、P2→P3、(P0,P3)→P5。P4はP0の中間フォーマットに合流するので独立に足せる。

## 10. 未確定の決定事項（実装前に確定する）

1. `type:'delivery'` を `orders` ストアに相乗りさせるか、最初から薄い `deliveries` ストアを分けるか。
2. 中間フォーマットCSVの列確定（必須／任意、単位・入数の表現）。
3. リードタイム・安全在庫の既定値（仕入先別 or 店一律）と、履歴からの推定精度の閾値。
4. 発注理論値を「保存せず都度算出」か「schedule変更トリガでキャッシュ」か。
5. レシピの保存先（localStorage → D1移行のタイミング）と共有の是非。
6. LLM抽出を将来入れる場合のプライバシー設計（自前Worker・マスキング・同意UX）。
